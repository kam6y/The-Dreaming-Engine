# AI統合仕様 — DreamMaster

ゲーム実行中の生成AI呼び出しを担うサーバー側モジュール「DreamMaster」の仕様。
防御要件は `ai-guardrails.md` が正であり、本書と矛盾する場合はguardrailsが優先。

## 全体像

```
ブラウザ(Phaser)                サーバー(Fastify)                    Claude
    │  WebSocket                     │
    ├── 会話開始/発言 ──────────▶ DreamMaster ── Agent SDK query() ──▶ claude-haiku-4-5
    │ ◀─ 検証済み発話(全文) ─────┤   │ カスタムMCPツール呼び出し
    ├── 宿泊(夢シーン要求) ─────▶   │   ▼
    │ ◀─ 夢の描写+世界変化 ──────┤ ツール検証層(純TS) ──▶ 承認された変更のみ
    │                               │   ▼                    GameStateへ適用
    │                               │ 監査ログ(logs/)
```

- **GameStateの正本はサーバーが保持する**。クライアント(Phaser)は描画と入力を担い、
  操作イベント(移動先・戦闘コマンド・アイテム使用・会話送信等)をWebSocketで送信する。
  サーバーが決定論的に適用して結果を返し、セーブ・AI呼び出し・ツール検証はすべて
  サーバー側のGameStateに対して行う(guardrails第5層が成立する前提)。
  クライアント⇔サーバー通信はWebSocketに一本化する(RESTは使わない)
- サーバーは`127.0.0.1`にのみbindし、WebSocket/HTTPの`Origin`ヘッダを許可リストで
  検証する。WS同時接続は**1本のみを維持**する: Origin検証を通過した新規接続を
  受理する際、既存接続が残っている場合は**既存側を切断してから**新規を受け入れる
  (クラッシュ・リロード後のゾンビ接続で進行不能にならないため。Origin検証で
  拒否される接続は既存接続に影響を与えない。guardrails**第0層**参照)
- **接続確立時(再接続を含む)、サーバーは現在のGameStateスナップショットを
  クライアントへ送信して再同期する**。クライアントはこれを正として表示を再構築する
- Agent SDKはTypeScript版 `@anthropic-ai/claude-agent-sdk` を使用
- 認証は環境変数で抽象化する。**既定は `CLAUDE_CODE_OAUTH_TOKEN`**(サブスクの
  `claude setup-token`で発行する長期OAuthトークン。Claude Code本体の公式
  Authenticationドキュメントに記載された認証手段。検証日2026-07-02。
  オーナーの要望によりサブスク認証を既定とする)。どちらか一方を`.env`に置けば
  動くよう実装し、**両方ある場合は`CLAUDE_CODE_OAUTH_TOKEN`を優先**する
  (Claude Code/SDK自体の優先順位はAPIキーが上位のため、優先制御は認証抽象側で行い、
  選択した認証情報のみをSDKへ渡す)
- 注記: Agent SDKドキュメント上の標準は`ANTHROPIC_API_KEY`であり、サブスク認証を
  第三者向け製品(Agent SDK製を含む)で提供することは事前承認なしには許可されない。
  本プロジェクトは自分専用・ローカルのため該当しないが、SDK経由での動作自体は
  M4実装時に`pnpm test:ai-live`で確認すること。動作しない場合・レート制限が
  問題になる場合は、コード変更なしで`ANTHROPIC_API_KEY`に切り替えて続行できること
  (環境変数の差し替えのみ)
- 実装時はAgent SDK公式ドキュメントで最新のAPI(query、カスタムツール定義、
  システムプロンプト指定、モデル指定、許可ツール制御)を確認してから書くこと

## AIサンドボックス(必須設定)

ゲーム内AIは**ゲーム世界にのみ**作用できる。Agent SDKの設定で以下を厳守:

- 許可ツール: 本書で定義するカスタムMCPツールのうち、**現在の呼び出しフローで
  許可された部分集合のみ**(「呼び出しフロー別仕様」の表を参照。6種をグローバルに
  許可せず、呼び出しごとに許可ツールを設定する)。
  検証層でも「ツール ∈ 現在フローの許可集合」を二重に検査する(guardrails第1層)
- **組み込みツールの遮断は`allowedTools`だけに頼らない**。SDKの`allowedTools`は
  「事前承認リスト」であり排他的ホワイトリストではない(未記載の組み込みツールも
  存在し、permission modeの判定に落ちる)。次を機構レベルで満たすこと:
  - ファイル読み書き・Bash・WebFetch等の組み込みツールをSDK設定で除去または
    全面拒否する(`disallowedTools`での明示拒否、`tools`オプションでの非ロード等。
    実装時に公式ドキュメントで最新の機構を確認する)
  - `permissionMode: 'bypassPermissions'` は**使用禁止**。権限判定コールバック
    (`canUseTool`等)は「現在フローの許可集合にあるカスタムMCPツール」以外を
    すべて拒否する(**デフォルト拒否**)
  - 攻撃テストAで「ゲーム内AIから組み込みツールが呼び出せないこと」を機械検証する
    (guardrails参照)
- ファイルシステム設定(CLAUDE.md・settings等)の自動読み込みは無効化する
  (`settingSources`を空に設定。SDK既定では設定ソースが読み込まれ得るため明示する。
  開発用ドキュメント=本リポジトリのCLAUDE.md等がゲームプロンプトへ混入するのを防ぐ)
- システムプロンプトは `ai-guardrails.md` の世界観憲法を使う(プリセット不使用)
- 1呼び出しのターン数上限を設定する(会話: 6、GM処理: 8を初期値とする)
  (会話は実測でSDKのツール遅延ロード+合成メッセージ応答に2ターン消費し、
  初期値4では余裕がなかったため6へ引き上げた)
- 出力トークン上限を設定する(会話: 1000、GM処理: 2000を初期値とする)

## 呼び出しコンテキスト(ゲーム状態スナップショット)

毎回の呼び出しで、DreamMasterは以下をXMLタグ構造でプロンプトに組み立てる。
セーブデータそのものやゲーム内部IDの羅列は渡さず、必要最小限を日本語で整形する:

```
<world_state>      … ゲーム内日付/時刻帯、天候、直近の世界イベント(最大3件)
<player_state>     … レベル、HP/MP割合(数値でなく「健在/手負い/瀕死」等の言葉)、
                      所持品の要約、現在地
<quest_state>      … メインクエスト進行段階、受注中サブクエスト(最大3件)
<quest_targets>    … (サブクエスト生成時のみ)有効な依頼対象の候補一覧。
                      HuntTargetId/FetchTargetIdの名称+ID(ゲームエンジンが列挙から生成)
<npc_state>        … (会話時)相手NPCの人物設定(原本は`world-lore.md`3節)、
                      好感度(数値+言葉)、会話記憶要約、
                      今日の話題(下記「会話セッション管理」)
<conversation>     … (会話時)直近の会話ログ(最大10往復)
<recent_play>      … (夢シーン時のみ)当日の行動サマリ数行(訪問マップ・戦闘勝敗・
                      会話相手・受注/達成クエスト等。ゲームエンジンが機械的に生成。AI生成ではない)
<player_utterance> … プレイヤーの自由入力(データとして。詳細はguardrails)
<task>             … 今回AIに求める処理の指示(会話応答/夢シーン生成など)
```

これらのタグへ埋め込む可変テキストは、**出所を問わず**(プレイヤー入力だけでなく、
会話ログ・会話要約・噂・クエストtitle/description・`reason`等のAI生成テキストも)
`<` `>`を全角に置換してから注入する(二次インジェクション防止。guardrails第3層)。

## 会話セッション管理

- **1会話の境界**: 会話はNPCに話しかけた時に開始し、プレイヤーが会話を閉じた時
  (Esc、「別れる」選択、シーン離脱)に終了する。**応答待機中(AI呼び出し実行中)は
  会話終了操作を受け付けない**(応答の完了・失敗確定後に受け付ける。待ち時間は
  全体タイムアウトで有界)。WS切断等で応答待機中に会話が強制中断された場合は、
  進行中呼び出しの完了・失敗確定後に通常の会話終了処理を行う。会話終了時に要約生成と
  会話内カウンタ(`adjust_affinity`回数・`give_item`回数)のリセットを行う。
  「ゲーム内1日あたり」のカウンタ(`give_item`全NPC合算等)は会話を跨いで持続し、
  日送りでのみリセットされる(時間定義は`game-design.md`「ゲーム内時間」)。
  **1往復**=プレイヤーの自由入力送信1回とそれへのAI応答1回の組(AIの開始挨拶は往復に数えない)
- NPCごとに会話履歴を**サーバー側で**保持(未要約の直近往復(最大10)+それ以前の要約。
  更新規則は下記「要約の更新規則」)
- 会話ログ・プロンプト内の話者ラベル(「旅人」「NPC名」等)は**サーバーが付与する**。
  プレイヤー入力内の「宿屋の主人: 〜」のような話者ラベル風の書式はラベルとして
  解釈せず、そのまま発言内容(データ)として扱う(話者偽装による偽記憶の注入防止)
- 各NPCは**「今日の話題」スロット(1件)**を持つ: 初期値は`shared`で定義する
  NPC別のデフォルト話題。日送りでデフォルト値にリセットし、セーブに保存する
  (`game-design.md`「セーブ/ロード」)。会話時は`<npc_state>`に含めてプロンプトへ
  渡し、NPCが会話の中で自然に触れる。`trigger_world_event`の`npc_rumor`は
  このスロットを置き換える(出力壁を通過したもののみ保存: guardrails第5層)
- **段階別の態度指示(M11-2)**: 会話フローでは`<npc_state>`に好感度の数値・段階名
  (`shared`の`affinityTier`が導出する4段階: `game-design.md`「好感度の段階」)に加え、
  段階別の**態度指示(1-2文)**を添える。文言は`packages/server/src/ai/dream-master/prompt.ts`の
  固定定数(`AFFINITY_ATTITUDE_INSTRUCTIONS`)で一元管理する。目安は
  警戒=短く素っ気なく踏み込ませない / よそよそしい=丁寧だが距離を保つ /
  打ち解けた=口調が和らぎ自分の事情や噂を少し話す / 信頼=心を開いて率直に語り力になろうとする。
  **各NPCの人物設定が態度より優先**である旨も一文添える(態度は人柄の枠内で表す)。
  段階名・態度指示はサーバー管理の固定定数のため、可変テキスト(話題・記憶・発話)と異なり
  `neutralizeTags`は通さない(NPC名・人物設定と同じ信頼クラス。guardrails第3層の無害化流儀は不変)。
  段階割引と同様、態度指示はプロンプトへの提示のみで、ツール権限・検証(delta±10・1会話2回・
  日次±20・`give_item`解禁閾値50)は一切変えない
- 要約は**新規の往復が1往復以上あった会話でのみ**生成する。0往復で終了した会話
  (話しかけて即閉じた場合等)は要約呼び出し自体をスキップし、既存の履歴・要約を
  変更しない(サブスク枠の保護)
- 要約は会話終了時に生成AIで作成(ツールではなく別呼び出し、haiku使用、200字以内)。
  要約呼び出しも**DreamMasterインターフェースの一部**とし(`AI_MODE=mock`では
  固定要約を返す。実AIが混入しないこと)、世界観憲法・タグ分離・出力壁(第4層の
  フルセット: 照合前正規化・長さ・最小長・逸脱パターン・日本語比率)・監査ログを他フローと同様に適用する。
  失敗時(タイムアウト・エラー・**出力壁による却下**を含む)は要約を保存せず、
  末尾5往復をそのまま保持して代替する。**出力壁を通過した要約だけをセーブに永続化する**
  (guardrails第5層参照)
- **要約の更新規則(累積置換)**: 生成の入力は「既存要約+未要約の往復
  (前回からの持ち越し+今回の会話。`<conversation>`と同じ最大10往復)」。
  出力は**既存要約を置換**する(連結しない。常に1件・200字以内)。
  成功したら入力に含めた往復はすべて要約済みとして履歴から落とす(未要約往復は0件になる)。
  失敗時は既存要約を変更せず、未要約往復の**末尾5往復のみ**を持ち越して代替する(上記)。
  次の会話の`<conversation>`には「持ち越した未要約往復+今回の新規往復」を
  最大10往復で渡す(要約本体は`<npc_state>`の会話記憶要約として渡る)
- 好感度・会話記憶はセーブデータに含める(セーブ形式は`game-design.md`)
- Agent SDKのセッション再開機能には依存しない。コンテキストは毎回
  スナップショットから組み立てる(サーバー再起動・セーブロードに強い)

## カスタムツール定義(6種)

すべて入力をzodスキーマで定義し、**スキーマ検証→ゲームルール検証**の2段階を
通過したものだけをGameStateに適用する。検証層は純TSモジュールとして実装し、
ユニットテストを網羅する(境界値・違反ケース含む)。

### 1. `speak` — NPC発話(状態変更なし)

| 項目 | 内容 |
|---|---|
| 入力 | `{ text: string }` |
| 検証 | 空白除去後1字以上・400字以内。出力壁フィルタ(guardrails参照)通過 |
| 効果 | 会話ウィンドウに表示。サーバーがツール入力**全文**を受領し出力壁を通過させてからクライアントへ送出する(表示演出はクライアント側タイプライターの疑似ストリーミング。未検証テキストは送出しない)。**拡張(オーナー指示 2026-07-12)**: 会話・サブクエスト生成では生成中の `text` 増分を画面表示のみへ先行送出してよい(条件・撤回は `ai-guardrails.md` 第4層の例外規定。下記「対話応答のストリーミング表示」) |

### 2. `narrate` — 情景・戦果描写(状態変更なし)

| 項目 | 内容 |
|---|---|
| 入力 | `{ text: string }` |
| 検証 | 空白除去後1字以上・300字以内。出力壁フィルタ通過 |
| 効果 | ナレーションウィンドウに表示 |

### 3. `adjust_affinity` — 好感度変更

| 項目 | 内容 |
|---|---|
| 入力 | `{ npcId: NpcId(enum), delta: number, reason: string }` |
| 検証 | npcIdは**現在の会話相手と一致**すること。deltaは整数かつ-10..+10。適用後0-100にクランプ。1会話につき2回まで。<br>**日次累積上限**: 同一NPCに承認したdelta(申告値)のゲーム内1日の累積が±20の範囲を超える呼び出しは却下<br>(会話の開閉ではリセットされない。NPC別日次カウンタとしてセーブに永続化し日送りでリセット: `game-design.md`「ゲーム内時間」) |
| 効果 | 対象NPCの好感度を変更。reasonは監査ログにのみ記録 |

※ 好感度の段階(4段階への写像と商人の店の段階割引: `game-design.md`「好感度の段階(拡張: M11)」)は
**ゲームエンジン側の決定論的写像**であり、本ツールの権限・制約(delta±10・1会話2回・日次累積±20)、
`give_item`の解禁閾値50、その他のツール検証はいっさい変わらない(段階割引の適用にAIは関与しない)。

### 4. `give_item` — アイテム付与

| 項目 | 内容 |
|---|---|
| 入力 | `{ itemId: GiftableItemId(enum), quantity: number, reason: string }` |
| 検証 | itemIdは贈答ホワイトリスト(消耗品のみ、`shared`で定義)。quantityは**1-3の整数**。<br>当該NPCの好感度50以上(**会話開始時点のスナップショット値で判定**。同一会話内の`adjust_affinity`による上昇では解禁されない)。<br>インベントリの所持枠に空きがあること(満杯時は却下。満杯時の挙動は`game-design.md`「成長・経済」)。<br>1会話1回まで、ゲーム内1日3回まで(全NPC合算。<br>「1会話」「1日」の定義は会話セッション管理と`game-design.md`「ゲーム内時間」) |
| 効果 | インベントリに追加し「◯◯を受け取った」表示 |

### 5. `propose_quest` — サブクエスト発行

| 項目 | 内容 |
|---|---|
| 入力 | `{ type: 'hunt'|'fetch', targetId: HuntTargetId|FetchTargetId(typeに応じたenum), count: number, rewardGold: number, rewardItemId?: GiftableItemId, title: string, description: string }` |
| 検証 | countは**1-5の整数**。rewardGoldは**10-100の整数**かつ`count × 20`以下(報酬対難度の比検証)。<br>rewardItemIdは贈答ホワイトリスト内。rewardItemId付き提案は1ゲーム内日1件まで。<br>targetIdはtypeに応じた**達成可能ホワイトリスト**内であること(`GiftableItemId`と同様に`shared`の列挙で定義):<br>hunt=`HuntTargetId`(リスポーンする雑魚敵のみ。ボス「夢喰い」等リスポーンしない敵は含めない)、<br>fetch=`FetchTargetId`(購入・採取・ドロップで再入手可能なアイテムのみ。一点物のクエスト用アイテムは含めない)。<br>受注中サブクエストが3件未満。**未受諾の「提案」が残っている間は新たな提案を却下**(未受諾提案は同時1件の上限)。<br>propose_questの発行は1ゲーム内日3件まで。title40字以内、description200字以内、出力壁通過 |
| 効果 | クエストジャーナルに「提案」として追加。未受諾の「提案」は同時に1件のみ保持し、<br>未受諾のまま会話が終了したら破棄する。**プレイヤーが受諾して初めて有効化**<br>(受諾/辞退は提案の提示直後に**会話内の選択肢**で行う。会話終了後の受諾経路はない)。<br>達成判定・報酬付与・放棄はゲームエンジン側の決定論的コードが行う(放棄は`game-design.md`参照)。<br>**達成の意味論**: hunt=受注後の対象討伐数がcountに到達し、情報屋への報告で完了。<br>fetch=情報屋への報告時に対象アイテムをcount個所持していることが条件で、報告時に**count個をインベントリから削除(納品)**して完了。<br>報酬付与はいずれも報告時。fetch型は**納品→報酬付与の順**で処理し、納品で空いた所持枠は報酬受領に使える(満杯時の報酬保留は`game-design.md`「成長・経済」) |

※`deliver`型(配達)は「何を」「誰に」の2参照が必要で本スキーマでは表現できないため、
縦切りでは扱わない(BACKLOGの「サブクエストのテンプレート拡充」で入力スキーマごと拡張する)。
→ この拡張を下記「5b」で展開する(M19)。

### 5b. `propose_quest` の型拡張(拡張: M19)

5節の `hunt`/`fetch` に、BACKLOG「サブクエストのテンプレート拡充」の3型
(`deliver`/`escort`/`survey`)を**追加**する。既存2型と既存の全検証(count 1-5・
rewardGold 10-100 かつ `count × 20` 以下・rewardItemId 贈答ホワイトリスト内・
rewardItemId付き提案1日1件・受注枠3件未満・未受諾提案1件・発行1日3件・
title40字/description200字・出力壁通過)は**そのまま全型に適用**する(以下は追加規則のみ)。
発行フロー・ツール許可(サブクエスト生成=speak+propose_quest)・報告先(すべて情報屋カイ)は不変。

**入力スキーマ(discriminated union の追加分)**:

| type | 型固有フィールド(2参照系) | count の意味 |
|---|---|---|
| `deliver` | `parcelId: DeliverParcelId`(何を=預かり品)+ `recipientId: DeliverRecipientId`(誰に=受取NPC) | 手渡す預かり品の個数(既存レンジ1-5) |
| `escort` | `destinationId: EscortDestinationId`(既存マップの指定地点) | **1固定**(1回の道行き。追加規則: count≠1 は却下) |
| `survey` | `targetId: SurveyTargetId`(既存マップの調べオブジェクト) | **1固定**(1地点の調査。追加規則: count≠1 は却下) |

- 型ごとに `targetId` 系フィールドの**名前と enum が異なる**ため、`hunt`/`fetch` と同じく
  `discriminatedUnion("type", …)` で表現する(型不一致・混成フィールドはスキーマ段で綺麗に却下)。
- **ホワイトリスト(すべて `shared` の列挙で定義。`GiftableItemId` と同様)**:
  - `DeliverRecipientId`: 会話可能NPC(`NpcId`)から**情報屋 `informant` を除いた**部分集合
    (受注元へ配達する無意味なクエストを防ぐ)。初期候補: `innkeeper`(オルガ)/`merchant`(レンド)/
    `priest`(フィオル)/`artisan`(ガロ)。
  - `DeliverParcelId`: 預かり品=**クエスト用アイテムの新設ホワイトリスト**(別枠管理・所持上限対象外・
    売却/破棄不可。`game-design.md`「成長・経済」)。専用スプライトは必須にせずクエスト用アイテムの
    共用アイコンでよい(`asset-pipeline.md`)。初期候補(語彙は裁量・M19-2で確定): `sealed-letter`(封緘の文)/
    `warm-oil-flask`(灯火の油壺)/`amber-charm`(琥珀の護符)。※既存の一点物 `old-key` は含めない。
  - `EscortDestinationId`: 既存11マップの**通行可能な到達地点**のホワイトリスト(新IDだが座標は実在・walkable)。
    初期候補: `town-gate`=灯町・南門の内側 `town(11,13)` / `settlement-gate`=琥珀郷・南門の内側 `settlement(8,10)` /
    `field-crossroads`=忘れ野・十字路 `field(11,8)`。
  - `SurveyTargetId`: 既存マップの**調べオブジェクト(`sign` 種)**のホワイトリスト。初期候補(実在オブジェクトID):
    `field-sign-post`(忘れ野の道標)/ `d1-sign`(裂け目一層「灯を絶やすな」)/ `town-sign-tavern`(霧笛亭の看板)/
    `settlement-sign-mine`(琥珀郷・坑口の看板)。**除外**: `d4-conduit`(第2章開始トリガー=`game-design.md`)、
    `chest`(一度きり開封)・`gather`(採取=アイテム源)は含めない(調べが無害・再実行可能な `sign` に限る)。

**達成の意味論(`hunt`/`fetch` と同じ粒度。報告先はすべて情報屋カイ・報酬付与は報告時)**:

| type | 受諾時 | 達成(→ `completed`)条件 | 報告時の処理 |
|---|---|---|---|
| `deliver` | 情報屋カイから預かり品 `parcelId` を `count` 個受領(クエスト用アイテム別枠へ。所持上限対象外=満杯でも受領可) | 受取NPC `recipientId` に話しかけて**納品**(決定論の選択肢会話。AI非依存)。納品時に預かり品を別枠から削除して `completed` | 報酬(gold+任意 rewardItem)を付与。**納品はすでに済んでいるので所持品の削除はしない** |
| `escort` | 同行者マーカーが出現しプレイヤーに追従(既存スプライト流用/軽量表示。新アセット不要) | 目的地 `destinationId` の座標に到達で `completed`(同行者は道連れ)。**同行中の戦闘に同行者は関与しない**(戦闘中は待機し戦闘後に再合流) | 報酬を付与(所持品の削除なし) |
| `survey` | (特別な受領物なし) | 対象 `targetId` を現地で「調べる」で `completed`(既存の調べ演出はそのまま+達成マーク。AI非依存) | 報酬を付与(所持品の削除なし) |

- 報酬アイテム(rewardItem)の受領は既存 `fetch` と同じく**満杯時は受領を保留**する
  (クエストは `completed` を維持・報酬は消失しない: `game-design.md`「成長・経済」)。
  `deliver`/`escort`/`survey` は `fetch` と違い**報告時のインベントリ削除(納品)を伴わない**
  (`deliver` の納品は受取NPCへの手渡し時に完結済み)。
- `progress` フィールドの意味: `hunt` のみ討伐カウントに使う。`deliver`/`escort`/`survey` は
  達成が原子的(納品/到達/調べで一気に `completed`)なため `progress` は 0 のまま用いない。
- **放棄時**: `deliver` は未納品の預かり品を**回収(消滅)**する(別枠から削除。既に納品済みなら回収対象なし)。
  `escort` は同行者マーカーを消す。`survey` は副作用なし。いずれもペナルティなし・即時に受注枠を解放
  (`game-design.md`「メインクエスト」放棄規定)。

**モック応答(MockDreamMaster)**: 新型ごとに `speak` + `propose_quest`(実在ホワイトリストIDを使う)を返す
定型応答と、悪意応答モード(ホワイトリスト外の recipient/destination/target・混成フィールド・
escort/survey の count>1 等)を追加する(実装はM19-3。検証層の却下をE2E/攻撃テストで通す)。

**旧セーブ互換(GAME_STATE_VERSION 据え置き可)**: `subQuest` スキーマへの union 追加は
**上位集合化**であり、旧セーブは既存の `hunt`/`fetch` のみを持つため引き続きパースできる(後方互換)。
`deliver` の預かり品も旧セーブには存在しない(別枠は空)。よって `GAME_STATE_VERSION` は **1 のまま据え置き**でよい
(本プロジェクトの互換方針は「新コードが旧セーブを壊さない」。新型を含む新セーブを旧コードで読む逆方向は非対象)。

### 6. `trigger_world_event` — 世界変化(夢シーン専用)

| 項目 | 内容 |
|---|---|
| 入力 | `{ event: WorldEvent }`(下記のdiscriminated union) |
| 検証 | 定義済み型のみ。1回の夢シーンで最大3件。テキスト系フィールドは出力壁通過。<br>累積適用の結果が各フィールドの定義レンジ内に**絶対クランプ**されること(検証層の責務。<br>例: dungeon_shiftを何晩重ねてもシンボル数はレンジ外に出ない) |
| 効果 | 翌朝の世界状態に反映 |

```ts
type WorldEvent =
  | { kind: 'weather'; value: 'clear'|'fog'|'rain'|'gloom' }
  | { kind: 'npc_rumor'; npcId: NpcId; rumor: string /* 120字以内。NPCの「今日の話題」を置き換え */ }
  | { kind: 'street_event'; eventId: StreetEventId /* 定義済み演出: 行商人/黒猫/鐘の音 等 */ }
  | { kind: 'dungeon_shift'; layer: 1|2|3; symbolCountDelta: -1|0|1
      /* 対象層(ダンジョン1-3層のみ。フィールドは対象外)の敵シンボル出現数の増減。
         適用後は対象層の定義レンジ(ダンジョン各層2-6体。マップ別レンジの正は
         game-design.md「マップ構成」)にクランプ */ }
```

※戦闘開始はシンボルエンカウント(`game-design.md`)であり「エンカウント率」は存在しない。
dungeon_shiftはシンボル出現数への作用として定義する。

※同一の夢シーンで同種`kind`が複数承認された場合の解決規則(検証層のテスト対象):
`weather`=後勝ち(最後に承認された1件のみ有効)。`npc_rumor`=同一NPCには後勝ち
(スロット置き換えの繰り返し)、別NPC宛ては併存。`street_event`=異なる`eventId`は併存、
同一`eventId`の2件目以降は却下。`dungeon_shift`=承認順に累積適用(クランプ規定どおり)。

### 6b. WorldEvent の型拡張(拡張: M20)

6節の `WorldEvent` union に、BACKLOG「夢シーンの演出強化」の3 kind
(`market_shift`/`npc_absence`/`dream_erosion`)を**追加**する。既存4 kind
(`weather`/`npc_rumor`/`street_event`/`dungeon_shift`)の定義・検証・解決規則・
絶対クランプの原則は**一切変えない**(以下は追加分のみ)。夢シーンのツール許可
(narrate+trigger_world_event)・処理順序(`game-design.md`「宿泊の処理順序」手順4で適用)・
一晩最大3件の上限(全 kind 合算で不変)も不変。新3 kind は**すべて決定論**であり、
AI が選ぶのは種類と定義済み選択肢のみ(効果量・対象は enum/ホワイトリスト。自由数値・自由対象は不可)。

**入力スキーマ(`shared` の `worldEventSchema` の discriminated union へ追記)**:

| kind | 型固有フィールド | 値域(定義済み enum のみ) |
|---|---|---|
| `market_shift` | `mode: MarketShiftMode` | 店の買値への一時倍率(下表)。翌日限り |
| `npc_absence` | `npcId: AbsentNpcId` | 翌日1日だけ不在にする NPC(ホワイトリスト。下記) |
| `dream_erosion` | `delta: -1\|0\|1` | 世界の侵食度(0-3)の一段階増減。累積・クランプ |

#### market_shift(市場の変化)

- **効果**: 翌朝の店頭の**買値**に一時倍率を掛ける。倍率は `shared` の `MarketShiftMode`
  enum から選ぶ(自由数値は受け付けない)。初期候補(値は M20-2 で確定):

  | mode | 意味 | 買値倍率 |
  |---|---|---|
  | `scarcity` | 品薄 | ×1.2(+20%) |
  | `surplus` | 供給過多 | ×0.9(−10%) |

- **寿命**: 翌日限り。`world.marketShift`(optional・default `null`)に保持し、
  日送り(`advanceDay`)で `null` にリセット=`activeStreetEvents` と同じ寿命
  (`game-design.md`「ゲーム内時間」)。宿泊手順4で適用されるため翌日の1日だけ効く。
- **同種解決規則**: **後勝ち**(承認された最後の1件のみ有効)。
- **合成順序(既存の好感度割引との合成。決定論。`shop.ts` で実装)**:
  `base = buyPriceOf(itemId)` → 好感度割引 `d = discountedBuyPrice`(既存写像)→
  市場倍率 `m = floor(d × 倍率)` → **絶対クランプ `max(1, m)`(最低1G)**。
  すなわち割引を先に、市場倍率を後に掛ける。
- **買い戻し増殖の防止(要注意・防御不変条件)**: `surplus` で買値が下がると
  「買値 < 売値」となり買い戻しでゴールドが増殖しうる。既存の `adjustedSellPrice` の
  不変条件(売値 ≤ 割引後買値)を、**market_shift 適用後の実効買値**に対して維持する
  (実効買値へクランプ)。これは既存防御の延長であり弱めてはならない
  (`game-design.md`「好感度の段階」売値クランプ)。
- テキスト系フィールドを持たないため出力壁の対象外。

#### npc_absence(失踪)

- **効果**: 指定 NPC が翌日1日だけマップから姿を消す(会話・店・宿が利用不可=
  「今日は姿が見えない」の定型表示)。翌日自動復帰(累積しない)。
- **安全設計(最重要)**: 対象は**消えても進行不能にならない NPC のホワイトリスト**
  `AbsentNpcId`(`shared` 列挙。`DeliverRecipientId` と同様に実在 `NpcId` の部分集合)に限る。
  初期ホワイトリスト: `innkeeper`(オルガ)/`merchant`(レンド)/`caretaker`(イルマ)/
  `artisan`(ガロ)の4名。**除外必須**: `priest`(フィオル=メインクエスト進行役)・
  `informant`(カイ=サブクエスト窓口)。番人 `warden`(トワ=第2章進行の担い手)も
  初期候補から除外する(`DeliverRecipientId` が warden を除くのと同じ方針)。
- **同時不在は1人まで**(後勝ち)。`world.absentNpc`(optional・default `null`)に保持し、
  日送りでリセット。同時1人ゆえ宿(innkeeper/caretaker)・店(merchant/artisan)は
  **同時全滅しない**(常に宿1・店1が残り、セーブ/購入経路が絶えず進行不能を作らない)。
- **deliver 型サブクエストとの相互作用**: 受取 NPC が不在の日は納品できず、クエストは
  `active` のまま翌日以降へ持ち越す(放棄は従来どおり可)。
- テキスト系フィールドを持たないため出力壁の対象外。

#### dream_erosion(夢の侵食度)

- **効果**: 世界の「侵食度」(0-3)を `delta: -1|0|1` で一段階増減する。
- **絶対クランプ 0-3**: `world.dreamErosion`(optional・default `0`)へ**承認順に累積適用**し、
  結果を 0-3 にクランプ(`dungeon_shift` と同じ累積+絶対クランプ。何晩重ねてもレンジ外に出ない)。
  **演出のみ**で、戦闘・経済・進行への決定論効果は一切持たせない(バランスへ非干渉)。
  侵食度は M20-3 でクライアント演出(画面 tint・霧の濃さ等)に用いる(既存 `tileTint` 系の重ね掛けで表現)。
- **段階名(0=平穏〜3=色濃い侵食。文言は M20-3 の裁量)**: 0=平穏 / 1=兆し / 2=綻び / 3=侵食。
- テキスト系フィールドを持たないため出力壁の対象外。

**同種解決規則(6節の書式に合わせる。検証層 `validateDreamEvents` のテスト対象)**:
`market_shift`=後勝ち(1件のみ有効)。`npc_absence`=後勝ち(同時1人)。
`dream_erosion`=承認順に累積適用(0-3 に絶対クランプ)。

**検証規則(追加方向のみ・既存不変)**:
- 定義済み enum 外(未知 `mode`・ホワイトリスト外 `npcId`・レンジ外 `delta`)は
  スキーマ検証/本体検証で却下する。
- **一晩最大3件は全 kind 合算で不変**(新 kind を混ぜても4件目以降は上限超過で却下)。
- 出力壁は**テキスト系フィールドを持つ kind のみ**に適用(新3 kind は該当なし。
  既存 `npc_rumor` の120字・出力壁は不変)。

**旧セーブ互換(GAME_STATE_VERSION 据え置き)**: `world` への追加フィールド
(`marketShift`/`absentNpc`/`dreamErosion`)はすべて optional + 既定値
(`null`/`null`/`0`)で補完し後方互換(旧セーブは未保持=非侵食・変化なしで読める)。
`worldEventSchema` への kind 追加も**上位集合化**であり、旧セーブは既存 kind のみを持つため
引き続きパースできる。よって `GAME_STATE_VERSION` は **1 のまま据え置き**でよい。
なお `game-design.md`「セーブ/ロード」保存内容の世界状態列挙へ新3フィールドを足すこと
(同節の「永続化前提の状態を追加したら列挙も更新」規定)は M20-2 で行う。

**モック応答(MockDreamMaster)**: 夢シーンの定型応答に新 kind の実在値を混ぜた
バリエーションと、悪意応答モード(ホワイトリスト外 `npcId`・enum 外 `mode`・レンジ外 `delta`・
新 kind を含む4件目)を追加する(実装は M20-2。検証層の却下を E2E/攻撃テストで通す)。

## 呼び出しフロー別仕様

| フロー | トリガー | モデル | 区分 | ツール許可 | タイムアウト(初回/全体) |
|---|---|---|---|---|---|
| NPC会話 | 話しかけ・自由入力送信 | haiku | 会話 | speak, adjust_affinity, give_item | 15秒 / 45秒 |
| サブクエスト生成 | 情報屋に「仕事はある?」 | sonnet | GM処理 | speak, propose_quest | 30秒 / 90秒 |
| 夢シーン | 宿屋に宿泊 | sonnet | GM処理 | narrate, trigger_world_event | 30秒 / 90秒 |
| 戦果描写 | 戦闘勝利(ボス・初見敵のみ。雑魚再戦は定型文) | haiku | 会話 | narrate | 10秒 / 30秒 |
| 会話要約 | 会話終了時 | haiku | 会話 | (ツールなし。テキスト出力に出力壁を適用) | 15秒 / 45秒 |

- 「区分」は「AIサンドボックス」のターン数・出力トークン上限のどちらの組を適用するかを示す
  (会話: 6ターン/1000トークン、GM処理: 8ターン/2000トークン)
- タイムアウトは2値で強制する: **初回**=初回トークン受信までの上限、
  **全体**=呼び出し開始から完了までの総時間上限(ストールしたストリームで
  ハングさせない)。いずれの超過も失敗として扱い定型フォールバックへ
- 各呼び出しのAgent SDK許可ツールは上表の集合のみに設定する(AIサンドボックス参照)
- **並行性(直列化)**: AI呼び出しはサーバー全体で**同時1件**に直列化する。
  呼び出し実行中に届いた新たなAIトリガー(会話開始・会話送信・宿泊の夢シーン・
  サブクエスト生成・戦果描写)はキューに積まず**拒否**し、会話系は定型文
  (例:「(……まだ言葉を紡いでいる)」)を表示、その他フローは定型フォールバックで
  進行する(いずれもAIを呼ばないブロックであり、縮退の失敗回数に数えない)。
  例外: 会話要約の実行中に**同一NPC**への新規会話開始が要求された場合は、
  要約の完了(または失敗確定)を待ってから会話を開始する(会話記憶の取りこぼし防止)
- 戦闘中はAIを呼ばない(ボス形態変化等の演出は定型文。`game-design.md`参照)
- 宿泊フローの処理順序(宿泊費徴収→回復→日送り→夢シーン→世界変化適用→セーブ)は
  `game-design.md`「ゲーム内時間」を参照。**AI失敗時もセーブは必ず成立する**
- モデルは `packages/server/config/ai.json` で変更可能にする
  (初期値: haiku=`claude-haiku-4-5`, sonnet=`claude-sonnet-5`)
- タイムアウト・エラー、または**表示系ツール(speak/narrate)の承認が0件**のターンは
  **定型フォールバック文**(シーン別に`shared`で定義、「…夢が霞んでいる…」等の
  世界観に沿った文)で進行。**この失敗ターンでは、承認済みの状態変更ツールも
  すべて破棄する(ターン単位のオール・オア・ナッシング)**。表示できる語りを
  一切持たないターンの状態変更は適用しない(`game-design.md`宿泊手順3の
  「世界変化なし」はこの規則の帰結)
- 本書で「失敗ターン」の判定・破棄の単位は**1トリガーのAI呼び出し全体**を指す
  (「AIサンドボックス」のターン数上限が数えるSDK内部のループ反復ではない。
  SDKループ反復単位での部分適用・部分破棄は仕様違反)
- 状態変更ツールだけが却下された場合、承認済みの発話は表示してよい。ただし
  効果表示(「◯◯を受け取った」等)は検証層の承認結果のみに基づいて出す
  (AIの発話がアイテム付与等を主張しても、承認がなければ効果も効果表示も発生しない)
- リトライは**タイムアウト・APIエラー・表示系承認0件の場合に1回**
  (thinking無効化+プロンプト強化で表示系0件の発生率は下げたが、非決定的な再発への
  保険として対象に加える)。**出力壁却下(summaryフローの要約却下)は引き続きリトライしない**。
  **1トリガーにつきリトライは最大1回**とし、失敗理由の組み合わせによらず2回目のリトライはしない
  (例: 初回タイムアウト→リトライ→成功したが表示系承認0件、の場合は表示系承認0件で確定し
  3回目の呼び出しはしない。サブスク枠保護)。**縮退モード**: 同一フローで
  3回連続の失敗(タイムアウト/エラー/表示系承認0件)が起きたら発動し、以降は
  全AIフロー(会話・サブクエスト生成・夢シーン・戦果描写・会話要約)を
  AI呼び出しなしの定型フォールバック文+選択肢のみで進行する
  - 失敗カウントは**トリガー単位**(1トリガー=最大1失敗): 初回とリトライの両方が
    失敗して初めて1失敗と数える。成功(リトライでの成功を含む)で連続カウントは0に戻る
  - **会話要約フロー(ツールなし)には「表示系承認0件」の失敗判定を適用しない**。
    同フローの失敗はタイムアウト・エラー・出力壁による却下の3種
    (「会話セッション管理」参照)であり、縮退の連続失敗カウントにはこの3種を数える
    (成功した要約を失敗扱いにしない)
  - 失敗に数えるのは**AI呼び出しを実際に行って失敗した場合のみ**。クールダウン・
    各種上限・宿泊費不足などによる「AIを呼ばないブロック」は失敗に数えない
  - 解除は日送りの完了時(宿泊手順2の直後。全滅帰還の日送りでも解除する)、
    またはサーバー再起動。宿泊による解除の場合、その宿泊の夢シーン(手順3)から
    実AIに復帰してよい
  - 縮退の**発動時および解除時に連続失敗カウントを0に戻す**(解除直後の1回の失敗で
    即再発動しない。再発動には改めて3回連続の失敗を要する)
  - ただし**セッション総数上限(下記)超過による縮退は日送りでは解除されない**
    (サーバー再起動または設定変更のみ。解除できると上限保護が無効化されるため)
  - 縮退状態はセーブに含めない

## レート・コスト保護(サブスク枠の保護)

- プレイヤー入力のレート制限: 会話送信は3秒に1回まで(クライアントとサーバー両方で)
- 同一内容の連続送信は拒否
- シーン別クールダウン(サーバー側で強制):
  - 会話開始(話しかけ): **同一NPCにつき実時間10秒に1回まで**。クールダウン中の
    話しかけでも会話自体は開けるが、開始時の挨拶はAIを呼ばず定型文で返す
    (話しかけ→即終了の反復による挨拶+要約の連打を防ぐ。要約側は
    「0往復はスキップ」の規定も参照: 会話セッション管理)
  - 夢シーン(宿泊): 実時間60秒に1回まで。クールダウン中の宿泊も宿泊処理
    (宿泊費徴収・回復・日送り・セーブ)は通常どおり行い、夢シーンのみ定型文で代替
    (AI呼び出しなし・世界変化なし)
  - サブクエスト生成: 実時間30秒に1回まで。受注中3件のときはAIを呼ばずに
    定型文で断る(呼び出し前にゲーム側でブロック)
- レート制限・クールダウン・カウンタは**サーバープロセス全体で単一**に管理する
  (WS接続・タブ・シーンインスタンスごとに分離しない。多重接続による並列回避を防ぐ。
  そもそもWS同時接続は1本のみ受け付ける: guardrails第0層)
- セッション(サーバー起動)ごとのAI呼び出し総数上限(初期値200、
  `config/ai.json`で変更可)。超過後は全フローを定型フォールバック文に縮退する
  (監査ログへの記録は継続。この縮退は日送りでは解除されない)。
  この上限は暴走(バグ・無限リトライ)からサブスク枠を守る回路遮断器であり、
  サーバー再起動という人間の明示操作でリセットされるのは意図した設計
  (外部からの悪用経路はguardrails第0層の境界で遮断する)。
  カウントは`AI_MODE`に依らず**DreamMasterインターフェースの呼び出し**に対して行う
  (単一機構。モックでも働くため、攻撃テストAで短い上限値により機構を検証できる)。
  通しE2E(モック)が途中で上限に達して縮退しないよう、**テスト設定では上限値を
  引き上げてよい**(機構の無効化・本番デフォルト値の変更は不可)
- レート制限・クールダウン・上限の各値は設定(`config/ai.json`)で変更可能にする。
  **テスト実行時に値を差し替えること(クールダウンの短縮、通しE2Eでのセッション
  総数上限の引き上げ等)は防御の弱体化にあたらない**。
  同様に、**テスト実行時のみのゲーム進行の加速**(XP倍率・移動速度・演出スキップ・
  デバッグワープ等の設定フラグ。モックAI・固定シードが前提で、本番デフォルトは無効)も
  防御の弱体化にあたらない(通しプレイE2Eを現実的な実行時間に収めるため)。
  防御要件は「本番デフォルト値が本仕様の値であること」と「制限機構自体が常に
  有効であること」の2点である(`ai-guardrails.md`冒頭の注記も参照)
- 雑魚戦の戦果描写など頻度の高いものは初回のみAI、以降は定型文
- `AI_MODE=mock` でDreamMasterを`MockDreamMaster`に差し替え可能にする。
  開発・E2Eは常にmockで行う(CLAUDE.md参照)。**フェイルセーフ**: `AI_MODE`が
  未設定・不正値(typo等)の場合は`mock`として扱い、実AIを使うのは明示的な
  `AI_MODE=live`のみ。さらにユニット/E2Eテストの実行下では`AI_MODE=live`を
  起動時エラーで拒否する(明示的な実AIテスト`pnpm test:ai-live`のみ例外。
  設定漏れによる実AI誤爆とサブスク枠消費を機構で防ぐ。攻撃テストAで検証)

## MockDreamMaster

- 本物と同じインターフェースを実装し、シーン別の決め打ち応答を返す
  (会話要約呼び出しも含む。`AI_MODE=mock`で実AI呼び出しが一切発生しないこと)
- ツール呼び出しもシミュレートする(例: 夢シーンで必ず`narrate`+`weather: fog`を発行。
  表示系承認0件だと状態変更ごと破棄されるため、状態変更を含む定型応答には
  表示系ツールを併せて含める)
  → ツール検証層・適用パスがE2Eで実際に通ることを保証する
- 攻撃リグレッションテスト用に「悪意ある応答モード」も持つ
  (ホワイトリスト外アイテム付与、上限超過など→検証層が却下することをテスト)

## 監査ログ

- `logs/ai/YYYY-MM-DD.jsonl` に1呼び出し1行で記録:
  タイムスタンプ、フロー種別、入力コンテキストのハッシュ、プレイヤー入力原文、
  応答テキスト、ツール呼び出しと検証結果(承認/却下+理由)、所要時間、モデル名
- 会話要約呼び出しも他フローと同様に記録する(監査の盲点を作らない)
- **境界・保護イベントも1行記録する**(AIを呼ばずに拒否/ブロックした場合):
  Origin不許可・Origin欠落による接続拒否、WS多重接続時の既存切断/新規拒否、
  レート制限・クールダウン・各種上限(セッション総数含む)による呼び出しブロック、
  縮退モードの発動・解除。記録項目はタイムスタンプ・イベント種別・理由。
  第0層・入力の壁の作動を事後監査できるようにする(攻撃テストAの検証対象)。
  **同種の境界イベントが短時間に連続する場合は集約して記録する**(例: 10秒の
  ウィンドウ内の同種拒否は件数をまとめて1行)。悪意ページの高頻度接続試行等で
  拒否記録自体が際限なく肥大しない(ログによるディスク圧迫の防止)
- 機密マスクは**監査ログへ書き込む全フィールドに無条件で**適用する
  (プレイヤー入力原文・応答テキスト・ツール入力・`reason`・エラー・SDK例外を含む。
  「エラー時のみ」ではない)。既知の機密パターン(認証系環境変数の値、
  `Authorization`ヘッダ、`sk-`/`sk-ant-`形式のトークン様文字列)をマスクしてから書き込む
  (例: プレイヤーが自由入力欄にAPIキー様の文字列を貼っても平文で永続化されない)
- 機密マスクは監査ログに限らず、**プレイヤー入力原文が平文で永続化される全経路**に
  適用する: セーブデータ内の会話履歴(未要約の直近往復)にも同じマスクを適用してから
  保存する(`game-design.md`「セーブ/ロード」・guardrails第5層参照)
- `logs/`はgitignore。ローテーションは日次ファイル分割のみで可

## AI応答キャッシュ・先行生成(拡張: M26)

BACKLOG「AI応答のキャッシュ・プリフェッチによる体感レイテンシ改善」の骨子。
本節は**「防御検証を通過した後の最終出力」だけを対象**とし、`ai-guardrails.md` の
いかなる防御層(第0〜6層)・ツール検証・出力壁・タグ無害化・レート/コスト保護も
**弱めず・迂回せず・省略しない**(追加のみ)。キャッシュ/先行生成が変えるのは
「AI呼び出しを実行するか、検証済みの結果を差し替えるか」だけであり、「呼び出しを許可するか否か」
の判定(直列化・クールダウン・送信レート・縮退・セッション総数上限)は現状と一切変えない。
実装のはめ込み口は `AiTurnExecutor`(`packages/server/src/ai/flow-control/turn-executor.ts`)の
「DreamMaster.run を呼ぶ直前/直後」であり、ゲートキーパーの保護判定は不変とする。

### 採用案

体感レイテンシに実効のある最小構成として、**単一のメモ化キャッシュ機構**を主軸に確定採用し、
**夢シーンの先行生成(オーバーラップ)**を条件付きで採用する。ほかのAI呼び出し点は
下記理由で**キャッシュ対象外**とする。

- **A. 表示専用ターンのメモ化キャッシュ(server純ロジック・確定採用)**:
  検証済みの `AiTurnResult` のうち **状態変更 effect を1件も含まない成功ターン**
  (`approvedEffects` が空・出力壁通過・フォールバック/縮退でない)だけを、フロー別の
  完全一致フィンガープリントで記憶し、同一フィンガープリントの次回呼び出しで
  **AIを呼ばずに検証済みテキストを即返す**。適用フローは次の2つ(いずれも同一機構):
  - **戦果描写(battleResult)**: 鍵=`enemyId`(コンテキストは `{flow, enemyId}` のみ=
    最も安全・決定論的な textbook ケース)。初見でAIが生成した検証済みナレーションを記憶し、
    以後の同種敵撃破で**待ち時間ゼロで初見の語りを再生**する(現状の「既見=定型文」を
    質・速度ともに上回り、AI枠も消費しない)。
  - **会話の開始挨拶(conversation の `playerUtterance:""` ターン)**: 鍵=完全文脈
    フィンガープリント(`partnerNpcId` ＋好感度＋今日の話題＋会話記憶要約＋受注クエスト集合の
    正規化ハッシュ)。同一NPCへ同一文脈で再度話しかけた際、挨拶を**即時**返す
    (最頻の待ち行為の一つを短縮)。**状態変更 effect を含む挨拶ターンは記憶しない**
    (`adjust_affinity` 等の副作用の二重適用を原理的に排除する)。
- **B. 夢シーンの先行生成=オーバーラップ(server+client・条件付き採用/縮退可)**:
  下記「プリフェッチ(採否と根拠)」参照。夢シーンの**出力はキャッシュしない**(当日プレイ反映=
  鮮度必須・`trigger_world_event` の副作用があり再生・二重適用は不可)。プリフェッチのみ対象。

### 対象外(効果が薄い/危険なため明記)

- **会話の自由入力送信(sendConversation)**: 自由入力で非決定的・鮮度必須・文脈依存が最大。
  同一入力への使い回しは没入を損ない鍵も肥大する。**キャッシュしない**。
- **サブクエスト生成(questGeneration)**: 依頼は毎回新規であるべき。使い回しは同一依頼の
  反復になる。**キャッシュしない**。
- **会話要約(summary)**: 入力(既存要約＋未要約往復)が毎回異なり鮮度必須。かつ会話終了時の
  背景処理でプレイヤーは応答を待たない(体感レイテンシが低い)。**キャッシュしない**。
- **投機的プリフェッチ(NPC・宿への接近時などに未確定のまま先行生成)**: 接近後に立ち去ると
  空撃ち=AI枠の無駄消費(コスト増)となり「レート・コスト保護」に反する。**採用しない**。

### 対象と鍵(キャッシュ適格性と再検証省略の安全性)

- **記憶するのは「検証済みの最終出力」のみ**。フォールバック・縮退・出力壁却下・
  DreamMaster失敗・状態変更 effect を含むターンは**一切記憶しない**
  (汚染テキスト・却下結果・副作用がキャッシュに焼き込まれない。guardrails第5層の精神を踏襲)。
- **鍵は検証入力を完全に含む正規化フィンガープリント**。適格2フローの検証入力は小さく完全列挙
  できる(battleResult=`enemyId` のみ・挨拶=上記文脈のみ)。文脈が1要素でも変われば鍵が変わり
  **miss→通常のAI呼び出し+全検証**へ落ちる(鮮度=好感度/話題/記憶/クエストの変化に追随する)。
- **ヒット時に再検証を省略してよい安全性根拠**: 出力壁・ツール検証は
  「入力バイト列→判定」が決定論の純関数である。鍵が同一=検証入力が同一バイト列
  ⇒ 判定も同一 ⇒ 記憶済みの結果は再検証してもバイト一致で承認される。ゆえに再検証は**冗長**で
  あり、その省略は迂回ではない(防御は記憶を作った miss 時に実行済みで、ヒットはその
  検証済み出力を再生するだけ)。**弱体化ではなく、同一入力への検証の再実行の省略**である。

### プリフェッチ(採否と根拠)

- **採用(条件付き): 夢シーンのコミット後オーバーラップ**。宿泊の処理順序
  (`game-design.md`「ゲーム内時間」)で **手順2(日送り)完了後の有料宿泊分岐**
  (`wasFree=false`。夢シーンのAI呼び出しが確定する地点)では、`<recent_play>` と翌朝の
  `<world_state>` がすでに確定し、かつ**夢の提示が確定している**。現状は宿泊ハンドラが
  夢シーンの呼び出しを await し終えてから全メッセージを一括送信する。先行生成では
  **日送り直後に「入眠」メッセージを先に送り、夢シーンの await をクライアントの入眠演出と重ねる**
  (演出後にスピナーを待つのでなく、演出の裏で最も遅い sonnet 呼び出しを進める)。
  **空撃ちは発生しない**(徴収・日送り済みで夢の消費が確定しているため。投機的発火はしない)。
  呼び出しは従来と**同一の1回**で、開始タイミングだけが演出に対して早まる。
- **不変条件の保持**: 世界変化の**適用順序は不変**(手順3で夢を待ち→手順4で
  `trigger_world_event` を適用→手順5でセーブ)。`<recent_play>`/`<world_state>` は日送り後に構築=
  現状とバイト一致。クールダウン(60秒)・`wasFree`・縮退の内部判定は `dreamScene` 内で従来どおり働く
  (クールダウン/無料宿泊/縮退時は定型で即返し=AI不呼び出し)。**AI失敗時もフォールバックで進行し
  セーブは必ず成立する**(2フェーズ化してもこの不変条件を保つ)。
- **実装は独立サブマイルストーン**: 入眠の途中演出を挟むため **WSメッセージの2フェーズ化**
  (「眠りにつく」→演出中に夢を生成→「夢の顕現」)と**クライアント演出**が要る=UI変更を伴う。
  リスク(2フェーズ化が宿泊順序・セーブ成立の不変条件を脅かす等)が出れば **cache-only へ縮退**
  (プリフェッチを見送り、BACKLOGへ差し戻し)してよい。

### レート・コスト保護との整合

- **キャッシュヒットはAI呼び出しではない**: セッション総数カウンタを**消費しない**
  (AI枠を使わないため。コスト保護を弱めるどころか余力を増す)。縮退の連続失敗にも数えない
  (失敗ではない)。**直列化・クールダウン・送信レートは現状どおり全て先に適用**され、
  ヒットは「呼び出しが許可された後にAIを実行する代わりに検証済み結果を差し替える」だけ。
- **縮退中はキャッシュを使わない**: `isDegraded()` の早期リターン(定型フォールバック)を
  現状のまま維持し、その後段でのみキャッシュを引く(縮退の意味を変えない)。
- **プリフェッチはコスト中立**: 同一の夢呼び出しを1回だけ行い、クールダウン・セッション総数の消費は
  従来と同数。投機的プリフェッチを採らないため無駄撃ちはゼロ。

### 永続化

- キャッシュは**メモリのみ・プロセス寿命**。**セーブにもディスク(`logs/`/`saves/`)にも一切
  書き込まない**(既存のランタイム保護状態=セッション総数・縮退フラグと同じ扱い)。
  サーバー再起動で消える。サイズは**有界**(フロー別に上限件数=LRU 相当)にし、無制限に肥大させない。
- 接続/セッション(WS再接続)を跨いでプロセス内で共有してよい(保護カウンタと同じくプロセス単一)。

### モック・テスト

- **`AI_MODE=mock` ではレイテンシが無く体感効果は観測できない**ため、**キャッシュ層は
  純ロジックとして直接ユニットテスト**する: 同一/別コンテキストでの hit/miss、
  状態変更 effect を含むターン・フォールバック/却下/縮退ターンが記憶されないこと、
  ヒットが `DreamMaster.run` を再呼び出ししないこと(モック呼び出し回数で検証)・
  セッション総数を増やさないこと、鍵の1要素変化で miss になること。
- **E2Eは不変**: モックは文脈決定論のため、ヒット再生とモック再呼び出しは**同一テキスト**を返し、
  既存E2Eの表示テキスト前提は保たれる。必要ならテスト用に `cache.enabled=false`(既定 true)を
  `config/ai.json` オーバーライドで与えて挙動を固定できる(本番デフォルトは変えない)。
- 既存の**攻撃テストA**・スモークE2Eの前提(クールダウン挨拶・0往復要約でAI不呼び出し等の
  モック呼び出し回数アサート)を壊さないこと。壊す場合はキャッシュのスコープ調整/フラグで対応し、
  **防御アサートは緩めない**。

### 観測点

- ヒット/ミス件数・推定短縮時間をプロセス内カウンタで集計(デバッグ用。秘密情報は持たない)。
- 監査ログにキャッシュヒットを1行残す(`ai_cache_hit`: フロー種別・コンテキストハッシュ・
  「AI枠不消費」注記のみ。生テキストは記憶を作った miss 時に記録済みのため不要)。
  機密マスクは他の全フィールド同様に無条件適用する。`logs/` はコミット禁止・秘密非記載を維持。

### 不干渉条件

- 6ツール定義・zod/ゲームルール検証・出力壁・タグ無害化・世界観憲法・`<world_state>` ほか
  XMLコンテキスト構築は**バイト不変**(鍵は現状構築されるコンテキストから導出するのみで、
  プロンプト・タグ・ツール入出力を一切変えない)。
- 既存ユニット/攻撃テストA/E2E(スモーク+`test:e2e:full`)が緑のまま。新ツール・新プロンプト・
  新 `<world_state>` フィールドを増やさない。`GAME_STATE_VERSION` 据え置き(キャッシュは非永続)。
- `ai-guardrails.md` の防御要件は**追加方向のみ**で扱い、いかなる層・検証・上限・クールダウンも
  弱めない・迂回しない。

## 対話応答のストリーミング表示(拡張: オーナー指示 2026-07-12)

会話(conversation)・サブクエスト生成(questGeneration)の `speak` を、生成中に増分で
クライアントへ先行表示する(設計書: `docs/superpowers/specs/2026-07-12-dialog-streaming-design.md`)。
防御上の位置づけ・必須条件(完了時の全文検証・撤回・非永続化・監査)は `ai-guardrails.md`
第4層の例外規定が正。

- **WSメッセージ**: `ai-stream-start {npcId}`(試行開始=表示バッファのクリア。各試行の最初の
  増分の直前に遅延送出)→ `ai-stream-delta {text}`(未検証増分)→ 従来の `ai-utterance`
  (最終正文=検証済み全文/定型文。ストリームの end/abort を兼ねる)
- **意味論は不変**: 直列化・クールダウン・送信レート・リトライ1回(リトライ時は
  `ai-stream-start` の再送でクライアント表示が消えて再開)・表示系承認0件・
  オール・オア・ナッシング・縮退・セッション総数上限・キャッシュ(ヒット時はストリーム無しで
  即時全文)は従来どおり
- **状態変更 effect の適用・効果表示は従来どおり最終検証後のみ**(ストリーム中に適用される
  状態変更は存在しない)
- 増分が1件も出ないまま失敗した試行では start を送らない(従来どおり定型文の `ai-utterance` のみ)
- 監査: `ai_call` 行に `streamed`(増分を1件以上転送)/ `retracted`(streamed かつフォールバック確定)
