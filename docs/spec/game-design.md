# ゲーム仕様 — The Dreaming Engine

## コンセプト

- ジャンル: 日本語のダークファンタジー2D RPG(見下ろし型・ターン制戦闘)
- 世界観の骨子: 世界は「夢見る機関(The Dreaming Engine)」が紡ぐ夢でできている。
  機関は壊れかけており、夢は綻び、悪夢が滲み出している。プレイヤーは記憶を失った
  旅人として、まどろみの街に流れ着くところから始まる
- トーン: 暗く、物哀しく、しかしどこか優しい。過度なゴア・グロテスク表現はしない
- 生成AIは「夢を紡ぐ機関の声」としてゲームに溶け込む。NPCの言葉の揺らぎや
  世界の変化は「夢だから」という世界観的必然を持つ
- 固有名詞・ロア・NPC人物設定の**正は `world-lore.md`**(街・NPC・敵の名前、
  性格・口調・秘密、用語集はそちらに従う)。`world-lore.md`に記載のない細部は、
  このトーンに合う範囲で実装者(Claude Code)が創作してよい。決めた内容はJOURNALに
  記録し、一貫して使うこと(新規の固有名詞は`world-lore.md`用語集にまず追記
  してから使う: 同書冒頭の規定)

## 画面・シーンフロー

```
タイトル画面 ──新規ゲーム──▶ オープニング(静止画+テキスト) ──▶ 街
     │                                                        │
     └──つづきから──▶ セーブ地点(街の宿屋)                 探索(フィールド/ダンジョン)
                                                              │
                                                    エンカウント ──▶ 戦闘シーン ──▶ 探索に戻る
                                                              │
                                                    ボス撃破 ──▶ エンディング ──▶ タイトル
```

- 解像度: 論理960x540(16:9)を基準にブラウザウィンドウへスケール
- Escでメニュー(所持品・ステータス・クエストジャーナル・設定・タイトルへ戻る)

### 全体マップUI「夢の地図」(拡張: M22)

「画面・シーンフロー」の探索中に、これまで巡ったマップの**全体像**を確認できる閲覧UIを
追加する。BACKLOG「ミニマップまたは全体マップUI」の展開。文言は「または」=片方でよいため、
**縦切りの精神(小さく完成)に沿って「全体マップ(キーで開くオーバーレイ)」のみを採用**する
(常時表示のミニマップは見送り=下記「採用案と根拠」)。世界観(この世界は機関が紡ぐ
**ひとつの夢**・`world-lore.md`1節)に沿い、旅人がまだ踏み込んでいない領域は**靄に沈めて伏せる**。
**新規画像アセットは不要**(矩形・線・テキストの手続き描画で成立=コード生成プレースホルダーの範囲)。

#### 採用案と根拠

- **採用: 全体マップオーバーレイ(探索中に `M` で開閉・`Esc` で閉じる)**。既存のオーバーレイ
  (もちもの/クエストジャーナル/店/会話/夢)と同じ開閉の流儀に乗せる(実装コスト・回帰リスクが最小)。
  マップ間の**接続グラフ**(ノード=マップ、エッジ=遷移)を俯瞰し、現在地を強調、
  **訪問済みマップのみ表示**、未訪問は靄で伏せる。
- **見送り: 常時表示のミニマップ**。ワールド/UIのカメラ分離・毎フレームのプレイヤー追従・
  リサイズ追従が要る一方、画面は既にHUD(左上ステータス)・キーヒント(右下)・侵食tint等が
  占めており、常時の小地図は情報過多。全体マップの方が「巡りの記憶」という世界観価値が高く、
  静的なマップ登録簿(`shared`の`MAPS`)から安価に描ける。
- **現在マップのタイル俯瞰(歩行可否・出入口の小さな見取り図)は本マイルストーンの対象外**とし、
  接続グラフの全体マップのみをM22の成果物とする(タイル俯瞰が要るとなれば別項目として切り出す。
  縦切りの精神=1機能ずつ完成)。

| ノード | 訪問済みの各マップを矩形+`displayName`(`world-lore.md`の固有名)で表示。**未訪問は靄**(暗い矩形+「？」等、名は伏せる) |
| エッジ | マップ間の接続(遷移由来の**無向グラフ**)。両端が訪問済みの辺のみ描く(未踏の先は靄) |
| 現在地 | いま居るマップのノードを強調(枠色=灯の琥珀 `#c9a25c` 等) |
| 凡例/操作 | 「M/Esc: 閉じる」の一行。オーバーレイのタイトルは「夢の地図」 |

- 対象は既存の全マップ(`mapIdSchema` の実体=下表の8枚)。接続グラフと各マップの
  `displayName` は静的な `MAPS` 登録簿から導出し、**新マップは増やさない**(閲覧のみ)。

  | mapId | displayName | ノード配置の目安 |

  共有座標系を持たないため、配置はグラフの**幾何(座標)**であり、**隣接(辺)**とは別物である
  (下記「データ設計」で担当を分ける)。

#### データ設計(訪問済み記録・接続グラフ・view)

- **訪問済みマップの記録 `visitedMaps`**(新規): `GameState` へ `mapId` 配列を
  **`optional`+`default([])`** で追加(M20の `world` 拡張と同じ後方互換の流儀。
  `GAME_STATE_VERSION` は **1のまま据え置き**=旧セーブは `default` で補完して読める)。
  - 新規ゲーム: 開始マップ(`town`)を初期値に入れる。
  - マップ遷移が成立するたびに行き先 `mapId` を(未収録なら)追記する。
  - つづきから/ロード時、`location.mapId` が未収録の旧セーブは現在地マップを補完する
    (`default([])` で読めた旧セーブでも、少なくとも現在地は必ず訪問済みになる)。
  - `advanceDay`(宿泊・全滅帰還)では**持続**(探索進捗であり日次リセット対象ではない)。
- **接続グラフ(隣接)**は `shared` の**純ヘルパー**として、全マップの `transitions` から
  **無向の隣接**を導出する(重複辺は畳む)。テスト可能な決定論的関数(`Phaser` 非依存)。
- **view露出**: `SnapshotView` へ `visitedMaps`(`mapId` 配列)を追加する。接続グラフと各マップの
  `displayName` は静的な `MAPS` 登録簿からクライアントが直接引く(クライアントは既に `MAPS` を
  `import` している=`exploration-scene` が使用)。したがって**view に増やすのは `visitedMaps` のみ**
  (現在地 `location` は既にviewにある)。

#### セーブ/ロードへの影響

- `visitedMaps` は永続化する(探索進捗)。「セーブ/ロード」の保存内容列挙にも
  `visitedMaps` を追記済み(拡張: M22。`optional`+`default([])`・`version` 据え置き)。
  保存内容の列挙は当該節の指示どおり、永続化状態の追加と同時に更新する。
- 旧セーブ互換: `version` は1のまま。旧セーブ(`visitedMaps` 欠落)は `default([])` で読め、
  ロード時に現在地マップが補完される。マイグレーション実装は不要。

#### UI・演出の骨子(実装詳細はM22-3)

- 開閉キーは `M`(地図)。既存の常設キーヒント(右下)に「M: 地図」を1項目追加する。
- オーバーレイは**探索シーンでのみ**開ける。他のオーバーレイ/ダイアログ表示中・
  会話/店/宿/夢の最中は開かない(クエストジャーナルと同じガード)。
  戦闘シーン・会話・夢シーンには持ち込まない(探索限定でよい)。
- 靄の表現: 未訪問のノード/エッジは低彩度・低不透明の矩形で伏せ、名を出さない
  (`world-lore.md` の靄・霧のトーン)。数値は出さず雰囲気で示す。
- E2E観測点(data属性): `#game` の `data-menu` に `"map"` を追加(既存の
  `inventory`/`journal`/`none` と同じ枠組み)。加えて `data-visited-count`(訪問済みマップ数)を
  新設し、探索で新マップへ移ると増えることを観測できるようにする。

#### 不干渉条件(必須)

- メインクエスト第1章・第2章の進行、既存E2E(スモーク+`test:e2e:full` 通し)、既存の
  移動・戦闘・会話・セーブの挙動を一切変えない(全体マップは**追加**の閲覧UI)。
- 既存の移動経路(忘れ野の `x=11` 縦断等)・遷移・マップ定義を変えない(閲覧のみ)。
- 新マップ・新敵・新アセットを増やさない(既存マップ登録簿の再利用)。`AI_MODE`・AIツール・
  防御仕様(`ai-guardrails.md`)は不変(本UIはAI非依存の描画のみ=`ai-integration.md`/
  `ai-guardrails.md` は触らない)。

### 好感度の段階(拡張: M11)

好感度(0-100)を4段階へ写像する。段階は保存しない導出値であり、
`shared`の純関数(`affinityTier`)が正。境界は`give_item`の解禁閾値50と
整合させる(**50が段階境界**)。

| 段階 | 好感度 | 名称 |
|---|---|---|
| 1 | 0-19 | 警戒 |
| 2 | 20-49 | よそよそしい(初期値30はここ) |
| 3 | 50-79 | 打ち解けた |
| 4 | 80-100 | 信頼 |

段階の効果:

- **(a) 態度**: 段階別の態度指示をliveプロンプトへ渡す(M11-2で実装。
  渡し方・文言は`ai-integration.md`)
- **(b) 決定論的効果 — 商人(レンド)の店の段階割引**(ゲームエンジンの
  決定論的コードが適用する。AIは価格決定に関与しない):
  - 買値: 警戒・よそよそしい(0-49)=**割引なし(従来価格と完全同値)**/
    打ち解けた=**5%引き** / 信頼=**10%引き**
  - 売値: 信頼のみ**5%増し**(それ以外の段階は従来どおり)
  - 端数規則: 割引額・増額とも `floor(基準価格 × 率)`(1G未満切り捨て)。
    割引後買値 = 買値 − floor(買値 × 率)、増加後売値 = 売値 + floor(売値 × 率)
  - 増加後売値は**同じ好感度での割引後買値を上回らない**
    (店で購入できる品(買値>0)に適用。買い戻し往復によるゴールド増殖の防止)
  - 適用順序: 売値5%増しのサーバー適用とUI表示は**M11-3で同時に**行う
    (表示額と実受取額の不一致を作らないため。M11-1では買値割引のみ適用する)
- **(c) UI**: 会話画面での関係性の暗示表示(数値は出さず段階の雰囲気のみ。M11-3で実装)

`give_item`の解禁閾値50(会話開始時点のスナップショット値で判定)・
`adjust_affinity`の制約(delta±10・1会話2回・日次累積±20)は従来どおり**不変**
(`ai-integration.md`「カスタムツール定義」)。

## メインクエスト(AI非依存で完結すること)

1. オープニング: 記憶を失った旅人が街に流れ着く
2. 司祭との会話(選択肢)で「夢の綻びの原因はダンジョン最深部の『夢喰い』」と知る
3. ダンジョン攻略(1層→3層。層ごとの小さな仕掛け: 鍵、スイッチ程度で可)
4. ボス「夢喰い」撃破
5. エンディング(静止画+テキスト)

- サブクエスト(AI生成)は情報屋経由で受注する任意コンテンツ。詳細は`ai-integration.md`
- 受注中サブクエストはクエストジャーナル(Escメニュー)からいつでも**放棄**できる
  (即時に受注枠を解放。ペナルティなし)。達成不能・不要なクエストで
  受注上限3件が恒久的に塞がらないための必須機能

### サブクエストの型拡充(拡張: M19)

情報屋カイが出す任意サブクエストに、既存の `hunt`(討伐)・`fetch`(納品)へ**3型を追加**する。
入力スキーマ・検証・達成の意味論の正は `ai-integration.md`「5b. propose_quest の型拡張」。
本節はプレイヤー視点の流れを記す(受注→遂行→報告はいずれも従来どおり情報屋カイが窓口)。

| 型 | 受注(カイから) | 遂行 | 報告(カイへ) |
|---|---|---|---|
| 配達(deliver) | 預かり品を「◯◯に届けてほしい」と託される。品は**クエスト用アイテム別枠**に入る(所持上限の対象外・満杯でも受領可・売却/破棄不可) | 指定NPCに話しかけて渡す(決定論の選択肢。預かり品が手を離れる) | 報酬(gold+任意で記念の品)。納品は済んでいるので所持品は減らない |
| 護衛(escort) | 「◯◯まで連れて行ってほしい」と同行を頼まれる | 同行者がプレイヤーに付いて歩く。指定地点に着けば達成(同行者は戦闘に加わらない) | 報酬 |
| 調査(survey) | 「◯◯を確かめてきてほしい」と頼まれる | 現地の対象を「調べる」で達成(調べた時の情景表示はそのまま) | 報酬 |

- **ジャーナル表示**: 既存の hunt/fetch と同じ枠で、型に応じた現況を1行で示す
  (配達=「〈受取NPC名〉へ 預かり品 ×N」、護衛=「〈目的地名〉まで同行中」、
  調査=「〈対象〉を調べる」)。文面(title/description)はAI生成のため出力壁通過済みのものを描画する。
- **放棄時**: いつでも放棄でき受注枠を即時解放(ペナルティなし)。**配達の未納品の預かり品は放棄で回収(消滅)する**
  (別枠から取り除く。売却/破棄不可の品がクエスト放棄後に残って所持を圧迫しないため)。護衛は同行者が去るのみ、
  調査は副作用なし。既に納品/到達/調べ済み(達成状態)なら回収するものはない。
- **所持枠との相互作用**: 配達の預かり品は別枠(所持上限対象外)のため受諾が満杯で阻まれない。
  報酬の品(あれば)は既存 fetch と同様、報告時に満杯なら受領を保留する(クエストは達成状態を維持・報酬は消えない)。
- **不干渉条件(必須)**: 第1章(`arrival`→`epilogue`)・第2章(`ch2-*`)の進行、既存の hunt/fetch サブクエスト、
  スモークE2E(14本)+`test:e2e:full` 通しを一切変えない(3型は**追加**であり既存経路に触れない)。
  護衛・調査・配達の遂行はすべて決定論(選択肢・調べ・到達判定)でAI生成に依存しない。
  新マップ・新敵・新アセットを増やさない(既存11マップ・既存NPC・既存調べオブジェクトの再利用)。

### 状態異常・属性の拡充(拡張: M21)

「ターン制戦闘」の状態異常(現状は毒1種のみ。上の`status.ts`「STATUS_DEFS」)を、世界観
(靄・霧・悪夢・灯)に沿って**2種追加**し、あわせて**耐性(=状態異常への「属性」)**の仕組みを入れる。
**既存の毒(`poison`)の仕様は一切変えない**(毎ラウンド終端に最大HPの5%(最低1)・継続3ラウンド・
上書き再付与)。新2種は**追加**であり、既存の戦闘・敵・スキル・バランスに触れないことを設計の起点とする。

#### 追加する状態異常(2種)

| id(裁量) | 名称(読み) | 効果 | 既定持続 | 重複規則 |
|---|---|---|---|---|
| `dazzle` | 眩惑(げんわく) | 付与中、その戦闘員の**攻撃行動が命中判定に失敗する確率**(既定25%)で空振りする(ダメージ0・付随状態異常も不発)。回復・バフ・アイテムには影響しない | 2ラウンド | 上書き(残ターンを定義値へリセット。毒と同じ流儀) |
| `dread` | 竦み(すくみ) | 付与中、その戦闘員の**行動開始時に既定30%で行動不能**(そのラウンドの行動を失う。プレイヤーは選んだコマンドが不発=MP/アイテム消費なし) | 2ラウンド | 上書き |

- 名称は`world-lore.md`のモチーフに合わせる。**眩惑**=灯・火の揺らめきや靄で視界が惑い狙いが逸れる。
  **竦み**=悪夢を前に身が竦む(既存の逃走失敗文「足がすくんで動けない」と同系のトーン)。
- 効果値(空振り率・行動不能率)・付与確率・持続はClaude Codeの裁量(M21-2/-3の`combat-balance.test`
  再検証で調整可)。上表は初期値。
- 定義は`status.ts`の`STATUS_DEFS`へ**表として1件ずつ追加**する一般形を保つ(battle.tsは種別を
  決め打ちしない)。効果種(命中低下=`accuracy`系、行動不能=`skip`系)は`StatusDefinition`の
  拡張として持たせる(毒の`tickDamage`はそのまま)。
- 眩惑・竦みの効果は**プレイヤー・敵の双方に成立する対称定義**とするが、縦切りの**割り当ては
  敵→プレイヤーを主**とする(下記)。

#### 付与確率と決定論(RNGの扱い)

- 技(敵move・プレイヤースキル)に**付与確率**フィールドを持たせる。**既定は1.0**(必ず付与)。
  既存の毒付与技(`poison-bite`/`nightmare-spew`/`murk-cleave`)は**1.0のまま**で挙動不変。
- **重要(バランス保存の要):** 状態異常に関わる乱数は**その状態が実際に関与する行動時のみ消費**する。
  すなわち (a) 付与確率が`1.0`の技は付与ロールをせず乱数を引かない、(b) 命中判定は行動主体が眩惑中の
  ときだけ、(c) 行動不能判定は行動主体が竦み中のときだけ乱数を引く。これにより、**新状態異常が一切
  絡まない戦闘のRNG列は現状と完全に一致**し、既存の`combat-balance.test`の統計値(勝率・全滅率・
  決着ターン)を**バイト一致で保存**できる(既存の毒挙動・シード再現性も不変)。

#### 耐性(=状態異常への「属性」)の仕組み

本マイルストーンの「属性」は、**状態異常の種別ごとの耐性**として実装する(古典的な炎・氷などの
ダメージ属性倍率テーブルは縦切りの世界観(灯・靄の世界であり炎氷雷の相性系ではない)と
バランス裕度の都合から**M21では対象外=別項目**とする。裁量として記録)。

- 各戦闘員は状態異常kindごとの**耐性値 0.0〜1.0(既定0=耐性なし)**を持つ。
  **実効付与確率 = 技の付与確率 ×(1 − 対象の耐性)**。耐性1.0で完全無効。
- **プレイヤー側の耐性は装備由来**(既存のレベル基礎値には持たせない=Lv由来の耐性は導入しない)。
  例として防具に状態異常耐性を持たせる(新規の護符または既存防具への付与はM21-3裁量)。
- **敵側の耐性は敵定義由来**(既定0)。
- 既定がすべて0のため、**耐性を明示付与しない限り現状と同一挙動**。`combat-balance.test`は
  装備なし(空装備)で測るため、装備由来のプレイヤー耐性は**テスト計測に一切影響しない**。
- **毒の耐性は新規付与しない(既定0を維持)**方針とし、既存の毒挙動(敵の毒付与・`murk-cleave`の
  ボスへの毒付与等)を保存する。耐性は主に新2種(眩惑・竦み)に用いる。

#### 既存の敵・ボス・スキルへの割り当て方針

`combat-balance.test`の統計対象(霧狼・迷い火・囁き仮面・錆喰い・紡ぎ損ない・夢喰い)を
**避けて割り当てる**ことで、既存閾値との衝突を構造的に排除する。統計対象**外**の
ダンジョン雑魚2種へ主に割り当てる:

| 敵 | 追加する状態異常 | 根拠(world-lore) | balance-test |
|---|---|---|---|
| 蝋燭喰らい(`candle-eater`) | **眩惑**(揺らめく火で視界を惑わす新move) | 4節「小さな火を宿す」 | **対象外**(閾値に非干渉) |
| 軋み人形(`creaking-doll`) | **竦み**(軋みが不安を掻き立てる新move。既存の毒付与技はそのまま併存) | 4節「関節が軋む/継ぎ接ぎの人形」 | **対象外**(閾値に非干渉) |

- 上2種は`combat-balance.test`の計測に現れないため、新moveの追加で**既存の統計閾値は変化しない**。
  ただし通しプレイ(`test:e2e:full`・加速)と自然進行を塞がないよう、付与確率・持続は控えめにし、
  解除手段(下記の灯アイテム)を用意して**ソフトロックを避ける**。
- **ボス「夢喰い」・中ボス「紡ぎ損ない」への付与は任意**とし、行う場合は第2形態(HP50%以下)に限る。
  両者は`combat-balance.test`の統計対象のため、付与すると乱数列が変わる。**採用の条件は再検証で
  全閾値(Lv6勝率≥70%・Lv5≥60%・Lv1-4全滅率≥90/80%等)を満たすこと**。満たせない場合は
  付与確率・持続を下げるか、その割り当てを見送る(M9-2の再検証と同じ流儀。緩める方向の変更は禁止)。
- **プレイヤー→敵の付与は任意(初期は見送り可)**。追加する場合、`combat-balance.test`の方策
  (`attackPolicy`/`bossPolicy`)は新スキル・新アイテムを使わないため、**追加自体は既存閾値へ非干渉**。
- **解除・対抗手段**: 現状は解毒薬が毒を治す(`cure-status`)。眩惑・竦みにも**灯/光**を典拠とする
  解除アイテムを設ける(例: 松明状の「灯明(ともしあかり)」で眩惑・竦みを鎮める。灯が暗がりと
  怯えを払うトーン。既存の`cure-status`効果種の拡張または新効果種はM21-3裁量。`old-key`等の
  クエスト用アイテム別枠・所持上限規則は不変)。

#### AI(DreamMaster)への波及

- **波及なし。** 戦闘中はAIを呼ばず(`ai-integration.md`「戦闘中はAIを呼ばない」)、状態異常・耐性は
  すべて決定論的な戦闘内部処理である。`narrate`は状態変更を伴わない演出専用ツール。
  したがって**AIツールの入出力スキーマ・防御仕様(`ai-guardrails.md`)は変更しない**
  (M19/M20と異なり、本マイルストーンは`ai-integration.md`/`ai-guardrails.md`を触らない)。

#### セーブ/ロードへの影響

- 状態異常は**戦闘中の一時状態(`BattleState`のみ)**で、戦闘外に持ち越さない(既存の毒と同じ)。
  よって**セーブ形式は変更しない**。耐性はレベル/装備から導出され(装備はセーブ済み)、
  **新規のセーブフィールドを増やさない**(`version`据え置き・旧セーブ完全互換)。

#### UI・演出の骨子(実装詳細はM21-3)

- バトルUIに眩惑・竦みの状態バッジ/ラベルを表示(既存の毒バッジと同じ枠組み。表示名は
  `STATUS_DISPLAY_NAMES`から引く)。
- 新イベント文言: 眩惑での空振り(「狙いが逸れ、刃は虚しく空を切った。」等)、竦みでの行動不能
  (「身が竦み、動けない。」等)、付与時・失効時・解除時のメッセージ(`STATUS_DEFS`の文言表から引く一般形)。
- 新規画像アセットは不要(テキスト+既存UI枠で成立)。耐性の暗示表示は任意(数値は出さず雰囲気のみ)。

#### 不干渉条件(必須)

- メインクエスト第1章(`arrival`→`epilogue`)・第2章(`ch2-*`)の進行、既存E2E(スモーク+
  `test:e2e:full`通し)、既存の毒・スキル・装備・敵の挙動を一切変えない(2種は**追加**)。
- `combat-balance.test`の全閾値を**緩めない**。新状態異常が絡まない戦闘のRNG列を保存し、
  絡む場合(ボス等に付与する場合)のみ再検証して閾値を満たすこと。
- 新マップ・新敵・新アセットを増やさない(既存11マップ・既存8敵の再利用)。

## スキル(拡張: M9)

「ターン制戦闘」の**スキル**を、レベル習得で5種に拡充する。既存2種(`ember-strike`/
`soothing-light`)は**Lv1習得のまま**で早期ゲームの挙動を変えない。名称は`world-lore.md`の
モチーフ(灯・機関・忘れられた願い・青灰の靄)に合わせる。数値(倍率・バフ量・ターン数・MP)は
Claude Codeの裁量で、MP経済(Lv1 maxMP10 → Lv10 maxMP44)と整合する初期値とする(M9-2で
`combat-balance.test`により再検証・調整可)。

| スキルID | 名称 | 習得Lv | 効果 | MP消費 |
|---|---|---|---|---|
| `ember-strike` | 焔の一閃 | 1 | 攻撃(攻撃力 × 1.8) | 4 |
| `soothing-light` | 安らぎの灯 | 1 | 回復(HP + 45) | 5 |
| `murk-cleave` | 澱み斬り | 3 | 攻撃(攻撃力 × 1.3)+ 敵に毒を付与(毒=毎ターン最大HPの5%) | 5 |
| `warding-stance` | 灯守りの構え | 4 | 自身に防御バフ(防御 + 8 を3ターン) | 6 |
| `blaze-ender` | 焔尽くし | 6 | 強撃(攻撃力 × 3.0) | 12 |

- 既存2種(Lv1習得): `ember-strike` 焔の一閃(攻撃 倍率1.8 / MP4)、`soothing-light`
  安らぎの灯(回復45 / MP5)。挙動不変。
- 新規3種の**効果種**(毒付与つき攻撃・自身の防御バフ・高倍率の強撃)は**M9-2で戦闘エンジンに実装済み**
  (この仕様表が先行して確定した)。M9-1では習得機構(導出・検証・UI一覧)のみを整えた。
- **M9-2 実装注記(効果種の確定挙動)**:
  - `murk-cleave` 澱み斬り: ダメージ適用後、**敵が生存している場合のみ**毒を付与する(この一撃で倒しきった
    敵には付与しない)。毒は既存仕様どおり毎ラウンド終端に最大HPの5%(最低1)。付与したラウンドの終端tickから
    効く(敵の毒付与技と同じ扱い)。毒の効果値・継続(3ラウンド)・文言は `status.ts` の状態異常定義表から引く。
  - `warding-stance` 灯守りの構え: 自身の**実効防御に +8**。継続「3ターン」は**付与ラウンドを1ターン目として数える**
    (付与ラウンド + 続く2ラウンドの被ダメージを軽減し、3ラウンド目の終端で失効=失効イベントを通知)。
    付与ラウンドでは、行動順で敵がプレイヤーより先に動いた分の攻撃には**まだ乗らない**(バフはプレイヤーの行動時点で発動)。
    **重ねがけ**は加算せず、量・残ターンを毎回定義値へリセット(上書き)する。
  - `blaze-ender` 焔尽くし: 攻撃力 ×3.0 の単発強撃(新機構なし)。
- **習得規則**: スキルは**レベルから純粋に導出**する。習得済み一覧は `skillsForLevel(level)` が返す
  (習得レベル昇順→同レベルは定義順)。**習得状態はレベルから一意に導けるため、セーブには保存しない**
  (保存対象外)。ロード時はセーブのレベルから同じ一覧が再現される。
- **習得レベル未満のスキルは戦闘コマンドで使用不可**。戦闘エンジンの検証(`validateCommand`)が
  未習得スキルを `skill-not-learned` として拒否し、ラウンドを進めない(既存の `unknown-skill` /
  `not-enough-mp` は不変。判定順は 未知ID → 未習得 → MP不足)。

## 成長・経済

- レベル1-10想定(縦切り)。経験値テーブル・能力成長は実装者が初期値を決め、
  「Lv1で最弱雑魚に3-5ターンで勝てる」「推奨Lv未満でのボス挑戦は高確率で全滅」を
  ユニットテスト(シミュレーション)で担保する
- 通貨: ゴールド。入手は戦闘・サブクエスト報酬。用途は店(消耗品)と宿泊費(少額)
- アイテム(縦切り): 回復薬(小/中)、解毒薬、松明(ダンジョンの暗がり演出用)、
  クエスト用アイテム数種。`shared`のアイテム定義に一元管理。
  **クエスト用アイテム(鍵等)は売却・破棄不可**(`shared`の定義にフラグを持たせ、
  店の売却対象と破棄操作から除外する。売却・破棄によるメインクエスト進行不能を防ぐ)
- インベントリには所持上限がある(ROADMAP M3。上限値は実装者裁量、JOURNALに記録)。
  **クエスト用アイテム(鍵等)は所持上限の対象外**(別枠管理。入手経路を問わず
  満杯でも常に受領できる。一点物の取り逃しによる進行不能を防ぐ。
  満杯時でも受領できることをユニットテストで担保する)。
  **満杯時の入手系の挙動**(通常アイテム):
  - AIの`give_item`: 検証層で却下する(通常の却下フロー。`ai-integration.md`参照)
  - 店の購入: 事前に容量チェックし、不足なら購入操作自体をブロック(「持ちきれない」表示)
  - サブクエスト報酬(アイテム付き): 報告時に容量不足なら受領を保留し、持ち物を
    空けるよう表示する(クエストは達成状態を維持し、報酬は消失しない)。
    fetch型は報酬処理の**前に納品**(対象アイテムcount個の削除)を行うため、
    納品で空いた枠も受領判定に使える(`ai-integration.md`「propose_quest」達成の意味論)
  - 戦闘ドロップ: 入らない分は破棄し「持ちきれなかった」表示(ゴールド・経験値は影響なし)
  - マップ上の取得(調べる・宝箱・仕掛け等): 満杯なら取得せず、対象はマップに残る
    (「持ちきれない」表示。持ち物を空けてから取り直せる。**破棄しない**)

## 装備(拡張: M8)

- 装備スロットは**2つ**: 武器(weapon)・防具(armor)。各スロットは装備品1つ、または空。
- 反映式(ダメージ式の**構造は不変**。攻撃力・防御力の入力が装備込みになるだけ):
  - 実効攻撃力 = レベル基礎攻撃力 + 武器の攻撃ボーナス
  - 実効防御力 = レベル基礎防御力 + 防具の防御ボーナス
  - ダメージ式は従来どおり `max(1, floor(攻撃力 × rand(0.9..1.1)) - floor(防御力 / 2))`
- 装備品は**アイテムの一種**(`shared`のアイテム定義に一元管理。装備用スロット・ボーナスを
  メタ情報として持つ)。装備・解除は**インベントリとの授受**:
  - 装備 = インベントリから1個消費してスロットへ収める
  - 解除 = スロットからインベントリへ戻す(**満杯なら解除不可**)
  - スロット使用中に別の装備をすると**入れ替え**(旧装備はインベントリへ戻る。新装備の除去で
    1枠空くため、**インベントリ満杯でも入れ替えは常に成功する**)
- 入手経路: **店での購入**(M8-3。上記4種を店在庫 `SHOP_STOCK` に追加済み。並び順は消耗品→武器(初級→上級)→防具(初級→上級))。売却可・クエスト用ではない
- 縦切りの装備品ラインナップ(初級/上級の2段階。性能・価格はゴールド経済と整合。
  数値はClaude Codeの裁量、ユニットテストで妥当性を担保):

  | ID | 名称 | スロット | ボーナス | 購入価格 |
  |---|---|---|---|---|
  | `worn-blade` | 錆びた片刃 | 武器 | 攻撃+3 | 60 |
  | `amber-blade` | 琥珀刃 | 武器 | 攻撃+7 | 180 |
  | `worn-cloak` | 擦り切れた外套 | 防具 | 防御+2 | 50 |
  | `warded-mail` | 灯守りの帷子 | 防具 | 防御+5 | 150 |

- 装備スロットは**セーブ対象**(「セーブ/ロード」の保存内容に記載)。M8-1 で追加した
  `equipment` フィールドは `.default()` 補完で旧セーブと後方互換(`version` 据え置き)。

## ゲーム内時間

- ゲーム内時間は「日付(1日目からの通し番号)」で管理する。**日送りは宿泊時と
  全滅帰還時のみ**(いずれも翌朝になる)。それ以外の行動で日付は進まない
- 全滅からの帰還(宿屋で目覚める)は、所持ゴールド半減の上でHP/MP全回復+日送りを行う
  (宿泊費の徴収・夢シーン・世界変化・自動セーブは行わない)
- 時刻帯は縦切りでは固定の演出値(例:「宵闇」)とし、`<world_state>`にはこの値を渡す
  (昼夜サイクルはBACKLOGの拡張)
- 「ゲーム内1日◯回」系のAI関連カウンタ(`give_item`回数、`propose_quest`発行数、
  `adjust_affinity`のNPC別日次累積等)は日送り時にリセットし、
  **現在日付とともにセーブデータに保存する**
  (セーブ&ロードでカウンタがリセットされる悪用を防ぐ)

### 宿泊の処理順序(順序厳守)

宿泊は次の順で処理し、途中でAIが失敗してもセーブまで必ず到達させる:

0. 宿泊費の徴収(定額の少額。初期値10ゴールド、`shared`の定数で定義)。
   所持金不足でも宿泊は**拒否しない**(無料で泊めてもらえるが、その晩の手順3は
   AIを呼ばず定型文で代替し、世界変化なし)。所持金0でもゲームが詰まないことを優先する
1. HP/MP全回復
2. 日送り(日付+1、日次カウンタのリセット)
3. 夢シーン(AI呼び出し。失敗・タイムアウト・クールダウン中・宿泊費不足は定型文で代替し、
   世界変化なし。失敗の定義(表示系承認0件を含む)と承認済み変更の破棄規則
   (ターン単位のオール・オア・ナッシング)の正は`ai-integration.md`「呼び出しフロー別仕様」)
4. 世界変化(`trigger_world_event`の承認分)の適用
5. セーブ(夢の結果・世界変化を含む状態を保存)

セーブが夢シーンの**後**にあるため、リロードで夢シーンのAI呼び出しが再発生したり
世界変化が再抽選されたりしない(サブスク枠の保護)。

### 夢の世界変化の拡充(拡張: M20)

宿泊の夢シーン(`trigger_world_event`)が起こす翌朝の変化に、3種の見え方を**追加**する。
入力スキーマ・検証・解決規則・クランプの正は `ai-integration.md`「6b. WorldEvent の型拡張」。
本節はプレイヤー視点の見え方と寿命を記す。既存4種(天候・噂・街頭演出・裂け目の気配)の
挙動は一切変えない。

| 見え方 | プレイヤーへの現れ | 寿命 |
|---|---|---|
| 市場の変化(market_shift) | 翌朝、店の買値がいつもと違う(品薄で高い/供給過多で安い)。好感度割引と合わさって値が動く | **翌日限り**(日送りでリセット) |
| NPCの不在(npc_absence) | 翌日、いつもの誰かが「今日は姿が見えない」。その NPC の会話・店・宿は翌日利用できない | **翌日限り**(翌朝の日送りで自動復帰。同時に消えるのは1人まで) |
| 世界の色(dream_erosion) | 世界の「侵食度」が深まる/和らぐと、画面の色みや霧の濃さが変わる(0=平穏〜3=色濃い侵食) | **累積**(日送りでは持続。段階は 0-3 にクランプ) |

- **市場の変化**は買値への一時倍率。定義済みの倍率(品薄/供給過多)からのみ選ばれ、
  自由な値幅は取らない。売値は「売値 ≤ 買値」の既存不変条件を市場適用後の買値に対して保ち、
  買い戻しによるゴールド増殖を作らない(「好感度の段階」売値クランプの延長)。
- **NPCの不在**の対象は、消えても進行不能にならない NPC(宿主オルガ/イルマ・商人レンド・
  職人ガロ)に限る。司祭フィオル(メインクエスト進行役)・情報屋カイ(サブクエスト窓口)・
  番人トワ(第2章の担い手)は不在にならない。同時不在が1人ゆえ宿と店は各1軒が常に開いている。
  配達サブクエストの受取相手が不在の日は納品を翌日に持ち越す(クエストは受注中のまま)。
- **世界の色**は**演出のみ**で、戦闘・経済・クエスト進行には一切影響しない
  (バランスを動かさない)。視覚表現は M20-3。
- **不干渉条件(必須)**: メインクエスト第1章(`arrival`→`epilogue`)・第2章(`ch2-*`)の進行、
  既存 E2E(スモーク+`test:e2e:full` 通し)、既存4種の世界変化の挙動を一切変えない
  (3種は**追加**であり既存経路に触れない)。新マップ・新敵・新アセットを増やさない。
  市場倍率・不在・侵食度はすべて決定論(AI は種類の選択のみ)。

### 昼夜サイクルと時間帯によるNPC配置(拡張: M23)

「ゲーム内時間」は日単位のまま(日送りは宿泊・全滅帰還のみ=上の記述は不変)を保ちつつ、
**1日の中に「時間帯」を持たせ**、時間帯に応じて灯町のNPCの立ち位置が変わるようにする。
BACKLOG「昼夜サイクルと時間帯によるNPC配置変化」の最小実装。本節は**純追記**であり、
既存の日付・宿泊・全滅・セーブ・世界変化(M20)・全体マップ(M22)の挙動を一切変えない。

**「ゲーム内時間」節の時刻帯(AIへ渡す固定演出値)との関係(重要)**: 上の「ゲーム内時間」に
ある「時刻帯は縦切りでは固定の演出値(例:「宵闇」)とし、`<world_state>` にはこの値を渡す」の
記述は**そのまま不変**とする。M23の「時間帯」は**ゲーム内の見た目とNPC配置にのみ作用する
別概念**であり、AI(`<world_state>`)への時刻帯の受け渡しは M23 では**変更しない**(AIへ
波及させない=`ai-integration.md`/`ai-guardrails.md` は触らない)。両者を混同しないため、
本節では一貫して「時間帯」(昼/夜)と呼ぶ。

#### 時間帯の粒度と進行規則(決定論)

- **時間帯は2段階(昼 / 夜)**とする(縦切りの精神=最小で成立。段階の追加は容易)。
- **進行(決定論)**: その日の探索で**プレイヤーの移動が実際に成立した歩数**を数え、
  一定歩数 `NIGHTFALL_STEPS`(`shared` の定数。初期値の目安 40 歩。**裁量**。実測で調整可)に
  達したら**昼→夜**へ移行する。夜は次のリセットまで持続する(昼へ自然には戻らない)。
- **リセット(必ず昼へ)**: 次のいずれかで時間帯は昼(朝)に戻り、歩数カウンタも 0 に戻る:
  - 新規ゲーム開始
  - 宿泊(「宿泊の処理順序」手順2の日送り=翌朝。夢シーン・世界変化の前後を問わず朝から始まる)
  - 全滅帰還(街で目覚める=翌朝)
  - セーブのロード(「つづきから」。理由は下「セーブ/ロードへの影響」)
- 移動以外の行動(調べる・会話・売買・メニュー操作)では時間帯は進めない
  (歩数のみを唯一の進行源とする=決定論で観測が容易)。
- 時間帯とその歩数カウンタは**サーバーのランタイム状態**として持つ(`mode` と同格の非永続。
  下記)。view(`SnapshotView`)に `timeOfDay`(`"day"|"night"`)を露出し、クライアントは
  これを描画とNPC配置に使う。

#### NPCの配置変化(灯町のみ・単一の正はshared純関数)

- **対象は灯町(town)のみ**(縦切りの最小)。第2エリア(琥珀郷=settlement)・フィールド・
  ダンジョンのNPC/敵配置は**時間帯で変えない**(既存の second-area / chapter2 E2E・戦闘導線に
  非干渉)。
- **配置の唯一の正は `shared` の純関数** `npcPlacementsForTime(map, timeOfDay)`(仮称)で、
  マップ定義の `npcs` に**時間帯別の上書き**(位置・向き)を適用した配置を返す。
  **サーバー(移動衝突・正面インタラクション・占有判定)とクライアント(描画)の両方が
  必ずこの同一関数を通す**(片側だけが夜配置を使うと「絵は夜の位置・話しかけは昼の位置」と
  乖離するため。`buildView` はNPC一覧を送らずクライアントが `MAPS` から引く現構造ゆえ、
  この一元化が正しさの要)。
- **夜の配置変化(縦切り分・裁量。座標は M23-2 で灯町グリッド上の歩行可能・非占有マスとして
  確定+検証する)**:

  | NPC | 昼(既定) | 夜 | 意味 |
  |---|---|---|---|
  | 商人 レンド(merchant) | 渡り物屋前 (16,4) 下向き | 霧笛亭(酒場)脇 ((7,11) 目安) 左向き | 店じまいして酒場で一杯 |
  | 宿屋 オルガ(innkeeper) | 灯宿前 (4,4) 下向き | **据え置き**(宿は夜こそ開く) | — |
  | 情報屋 カイ(informant) | 霧笛亭前 (4,10) 上向き | **据え置き**(酒場の窓口。夜も賑わう) | — |
  | 司祭 フィオル(priest) | 灯守堂前 (16,10) 上向き | **据え置き**(灯守堂に常駐) | — |

  縦切りでは**移動するのは商人1人のみ**(他3人は据え置き)。表にNPCを足すだけで拡張できる。
- **機能は時間帯で変えない**: 夜に位置が変わっても、そのNPCの**会話・店・宿の機能は昼と同じ**
  (店を時間帯で閉じる等の**経済・進行ゲートは入れない**=バランス・クエスト・防御に非干渉)。
  変わるのは立ち位置・向き・一言の彩りのみ。
- **M20 の `npc_absence`(不在)との整合**: M23 は**不在化ではなく移動**である。夜に配置が
  変わるNPCも**街内の到達可能・会話可能なマスに居続ける**(消えない)。したがって、
  メインクエスト進行に必須のNPC(司祭・情報屋・番人)や宿・店をソフトロックしない
  (そもそも移動対象は商人のみ)。`npc_absence` の翌日不在は従来どおり独立に効く。
- **ソフトロック不能条件(必須)**: 昼・夜のどちらでも、宿(オルガ)・店(レンド)・
  サブクエスト窓口(カイ)・メインクエスト進行役(フィオル)・第2章の担い手(トワ)へ
  必ず到達・会話できること。

#### 見た目(新規画像アセット不要)

- **夜の帳**: 夜はワールド全体に**藍色の薄い暗幕**(手続き描画の矩形。新規画像アセット不要)を
  重ねて時間帯を示す。M20-3 の**侵食の帳**(`dream_erosion` の暗紫矩形・深度 50)と共存させる:
  夜の帳を**侵食の帳より下**(深度は侵食の帳=50 未満)に置き、侵食(夢の綻び)が夜の上に
  さらに重なる序列とする。両矩形の合成 alpha が濃くなり過ぎないよう、夜の帳の alpha は控えめ
  (目安 0.16 前後。**裁量**、M23-3 で目視調整)。マップ別の乗算 tint(`tileTint`)は**変更しない**。
- **HUD**: 探索HUD(「N日目 …」)に時間帯の語を添える(例「2日目 昼」/「2日目 夜」。
  語は**裁量**、M23-3 で確定)。
- 侵食の帳と同様、UIレイヤー(別カメラ)には帳を掛けない。

#### セーブ/ロードへの影響

- **時間帯は保存しない**(`mode` と同格の非永続ランタイム状態)。理由: セーブは「宿泊の
  処理順序」手順5でのみ行われ、必ず手順2の日送り(→朝)の**後**に走るため、**あらゆる
  セーブは時間帯=昼の状態で取られる**。ゆえにロードは常に昼で再開でき、専用フィールドは
  不要(旧セーブとの互換は自明=新旧どちらのセーブも昼で読める。`GAME_STATE_VERSION` 据え置き)。
  この非永続の性質ゆえ、**上「保存内容」列挙・「保存しないもの」列挙は変更不要**(時間帯は
  そもそも保存対象に入らない)。
- 将来、朝以外のセーブ点を設ける場合に備えて永続化したくなったら、`world` へ
  `timeOfDay`(および歩数)を `optional`+`default` で足せる(`version` 据え置き=M20/M22 の先例)。
  縦切りでは非永続の最小案を採る。

#### AI(DreamMaster)への波及

- **波及させない**。時間帯は `<world_state>` へ渡さず(上「ゲーム内時間」節の固定演出値の記述は
  不変)、「今日の話題」・日次カウンタは日単位のまま変えない。`ai-integration.md`・
  `ai-guardrails.md` は**触らない**(会話・戦闘・世界変化はいずれも時間帯に依存しない)。

#### E2E・通しプレイへの不干渉

- **新規ゲーム・ロードは昼開始**。既存 E2E がNPCへ到達するのは新規/フィクスチャ開始から
  十数歩以内(昼)であり、`NIGHTFALL_STEPS`(目安 40)より十分小さいため夜へ移らない。
  移動スモーク(NPC非接触)は夜へ移っても影響しない。**M23-2 は既存 E2E(スモーク+`test:e2e:full`)が
  緑であることを閾値・配置の確定条件とする**(閾値だけに頼らない=下の固定フラグを併設)。
- **モック限定のテスト用フラグ**を新規ゲームオプションに足す(`startLevel` と同流儀=mock 時のみ尊重):
  時間帯を明示指定・固定する `timeOfDay: "day"|"night"`(仮称)。M23-3 のスモークは `"night"` で
  即座に夜を再現して配置変化と夜の帳を決定論的に観測でき、長い/将来の spec は `"day"` で
  昼固定にできる。防御弱体化にあたらない(`ai-integration.md`「レート・コスト保護」の注記)。

#### 不干渉条件(必須)

- 既存の移動・戦闘・会話・店・宿・セーブ/ロード・全滅帰還・メインクエスト第1/2章の進行、
  M20 の世界変化(市場・不在・侵食)、M22 の全体マップの挙動を**一切変えない**。
- 新マップ・新敵・**新規画像アセット**を増やさない(夜の帳は手続き描画)。
- AIツール(6種)・防御仕様(第1〜6層)は不変。時間帯は決定論(移動歩数のみが進行源)で、
  AI・乱数・経済・クエスト進行のいずれにも影響しない。

## セーブ/ロード

- セーブは**宿泊処理の一部(手順5)としてのみ**実行される。独立したセーブ操作
  (「休まず記録だけ」等)は提供しない。したがってセーブには必ず日送りが伴う
- GameStateの正本はサーバーが保持し、サーバーが`saves/save1.json`に保存する
  (スロット1。クライアントとの同期方式は`ai-integration.md`「全体像」参照)
- テスト実行時(E2E含む)は、セーブの出力先を環境変数でテスト専用ディレクトリに
  切り替える(人間のプレイセーブ`saves/save1.json`をテストが上書き・初期化しない)
- 保存内容(**この列挙が保存対象の正**。永続化前提の状態を仕様に追加したら
  本列挙も同時に更新すること):
  - プレイヤー状態(レベル・経験値・HP/MP・ゴールド)・位置
  - インベントリ
  - 装備スロット(武器・防具)(M8-1)
  - クエスト進行(メインクエスト段階・受注中サブクエスト)
  - マップギミックの解決状態(開けた扉・押したスイッチ・使用済みの鍵等、
    メインクエストの仕掛けの進行。ロードで巻き戻ると鍵消費型の仕掛けが進行不能になるため)
  - NPC状態: 好感度・会話記憶(要約+未要約の直近往復。未要約往復は機密マスク
    適用後のテキストを保存する: `ai-integration.md`「監査ログ」)・今日の話題(噂)
  - 世界状態: 天候・当日有効な`street_event`(複数可)・各層の敵シンボル数(`dungeon_shift`累積適用後)・
    当日の`market_shift`(買値倍率。翌日限り)・当日の`npc_absence`(不在NPC1人。翌日限り)・
    侵食度`dream_erosion`(0-3。`dream_erosion`累積適用後。持続)(拡張: M20。正は`ai-integration.md`「6b」)
  - 訪問済みマップ`visitedMaps`(全体マップUI「夢の地図」で訪問済みのみ表示するため。
    拡張: M22。`optional`+`default([])`・`version`据え置き。詳細は上「全体マップUI」)
  - 解除済み実績`unlockedAchievements`(「夢の欠片」の収集進捗。拡張: M24。
    `optional`+`default([])`・`version`据え置き。詳細は下「実績システム『夢の欠片』」)
  - 難易度`difficulty`(やさしい/ふつう/むずかしい。被ダメージ倍率のランタイム適用。拡張: M25。
    `default("normal")`・`version`据え置き。旧セーブ=ふつう。詳細は下「難易度設定」)
  - 戦果描写済みの敵種の記録(「初見」判定用。ロード後にAI呼び出しが再発しないため)
  - ゲーム内日付・AI関連の日次カウンタ(「ゲーム内時間」参照)
  - プレイ時間
- 保存**しない**もの(明示): 縮退モードの状態・実時間のレート制限/クールダウンの
  タイマー・セッションAI呼び出し総数(いずれもサーバープロセスの実行時状態。
  `ai-integration.md`参照)
- 書き込みは一時ファイルに書いてから`rename`で置き換える(原子的置換。
  書き込み途中のクラッシュで既存セーブを壊さない)。置換時に直前のセーブを
  `save1.json.bak`として1世代保持する
- zodスキーマでバージョン付き管理(`version`フィールド)。ロード時に検証し、
  `save1.json`が壊れていた場合は`save1.json.bak`からの復旧を先に試みる。
  両方壊れている場合のみエラー表示して新規開始を促す(クラッシュさせない)。
  **`version`不一致も縦切りでは破損と同扱い**(`.bak`復旧→駄目なら新規開始を促す)。
  拡張フェーズでセーブスキーマを変更する場合は、旧`version`からのマイグレーション
  実装とそのテストを当該ROADMAP/BACKLOG項目の完了条件に含める
  (アップデートで既存セーブを黙って無効化しない)
- タイトルの「新規ゲーム」は、既存セーブ(`save1.json`)が存在する場合、
  **上書き確認ダイアログ**を挟む(承諾するまで既存セーブ・`.bak`に触れない。
  実際の上書きは新規開始後の最初の宿泊セーブ時に起こる)

## 実績システム「夢の欠片」(拡張: M24)

BACKLOG「実績システム(夢の欠片収集)」の展開。プレイの節目を**実績=「夢の欠片」**として
収集・閲覧できるようにする。ロア上の位置づけ: 記憶を持たない旅人(`world-lore.md`1.4・3.1)の
内側に、心に残った出来事だけが**欠片**として結晶する——健忘という設定の対位となる
「旅人自身の記憶の器」である。悪夢(=夢の**断片**が渦を巻いた実体・同1.1)や
琥珀(=**灯の亡骸**・同2.4)、がらくた「機関の欠片」(アイテム)とは別語であり、
「夢の欠片」は旅人の記憶の結晶のみを指す(既存用語と衝突しない)。本節は**純追記**であり、
既存の進行・戦闘・経済・セーブ・AIの挙動を一切変えない。

### 採用案

- **実績は閲覧のみ**: 解除しても報酬・能力・進行・経済には一切影響しない
  (バランス・クエスト・防御に非干渉。「集める楽しみ」だけを足す最小実装)。
- **定義は `shared` の静的登録簿**(`ACHIEVEMENTS`。id・表示名・フレーバー・判定)。
  クライアントは `MAPS` と同流儀でこれを直接 import する(viewへ定義は載せない)。
- **各実績に1行のフレーバー文を持たせる**(採用。`world-lore.md` のトーンで、
  解除済みの一覧表示に添える。数値・攻略情報は書かない)。
- **解除は不可逆**: 一度解除された実績は取り消さない(条件が後で満たされなくなっても
  ——装備を外す等——解除済みのまま)。
- **判定はAI非依存の決定論**: 条件はゲーム状態(とサーバーの決定論イベント)のみから評価する。
  AI応答の内容を条件にしない(下「不干渉条件」)。

### データ構造

- `shared` に `achievementIdSchema`(英語kebab-caseのenum)と登録簿 `ACHIEVEMENTS`
  (初期セット12件=下表)を追加する。
- `GameState` へ **`unlockedAchievements`(実績id配列)を `optional`+`default([])` で追加**
  (M22 `visitedMaps` と同じ後方互換の流儀。**`GAME_STATE_VERSION` は1のまま据え置き**)。
  新規ゲームは空配列。`advanceDay`(日送り)では**持続**(収集進捗であり日次リセット対象ではない)。
- **条件評価は `shared` の純関数** `evaluateAchievements(input)`(Phaser非依存・ユニットテスト必須)。
  入力は「判定に必要な `GameState` の部分+ランタイム時間帯(`timeOfDay`)+当該操作で起きた
  決定論イベント列(`sub-quest-reported` / `world-event-applied` の2種)」、出力は
  「いま条件を満たす実績id集合」。サーバーは `unlockedAchievements ∪ 評価結果` で**単調更新**する
  (集合は増えるのみ=不可逆性の実装)。
- 初期セット12件は**既存の永続状態と上記2イベントだけで判定可能**なため、専用の進捗カウンタは
  追加しない。将来「悪夢をN体鎮める」等の累積型を足す場合は、`unlockedAchievements` と同流儀の
  `optional`+`default` カウンタを `shared` 純関数で扱う(骨子の拡張点)。

### 判定・解除フロー

- **評価点は単一チョークポイント**: サーバーが各クライアント操作の処理で `GameState` /
  ランタイムが変化した直後(スナップショット構築の前)に `evaluateAchievements` を呼び、
  解除集合を単調更新する。フック散在(移動・戦闘終了・装備・報告…に個別差し込み)にしない
  (漏れ・重複の温床)。イベント由来の2件は、当該処理(`report-quest` 成功・宿泊手順4の
  世界変化適用)がイベントを積んで**同じ評価**に渡す。
- **宿泊時の順序**: 手順4(世界変化の適用)の**後**・手順5(セーブ)の**前**に評価する
  (`woven-morning` の解除がそのまま当該セーブに載る。「宿泊の処理順序」自体は不変)。
- **解除してもサーバーは `dialog` を送らない**: 通知はクライアントのview差分トーストのみ
  (下「UI要件」)。既存E2Eの `dialog` 開閉観測・メッセージ順序に非干渉。
- 評価は純関数で**乱数を消費しない**(シード列・エンカウント・ドロップに影響しない)。

## 難易度設定(拡張: M25)

BACKLOG「難易度設定」の展開。プレイヤーが挑戦の重さを選べるようにする。**既定「ふつう」は
現行挙動と完全に一致(係数1.0=恒等写像)**させ、既存の戦闘計算・RNG消費順序・
`combat-balance.test` の統計・既存E2E・通しプレイを**無変更で緑のまま**保つことを設計の
絶対条件とする。本節は**純追記**であり、既定=ふつうのゲームの進行・戦闘・経済・セーブ・AIの
挙動を一切変えない(難易度は**ランタイム適用の乗算層**であり、敵定義・データテーブルには触れない)。

### 採用案

- **3段階**: やさしい / ふつう / むずかしい(id: `easy` / `normal` / `hard`)。**既定=ふつう**
  (新規ゲーム時のカーソル既定・旧セーブ補完値の両方)。
- **難易度が動かすのはプレイヤーの被ダメージ倍率のみ**(最小・明快)。**与ダメージ・獲得XP/
  ゴールド・ドロップ・命中率・状態異常付与確率・逃走率・経済(店価格)・敵ステータス・出現は
  難易度で変えない**。ゆえにバランス表・経済・実績(M24)・状態異常耐性(M21)・クエストは
  すべて**難易度非依存**を保つ。
- **ふつう=係数1.0=恒等**。現行の全計算式・RNG消費順序・`combat-balance.test` の統計値
  (勝率・全滅率・決着ターン)を**バイト一致で保存**する(根拠は下「適用点」)。
- 係数は**戦闘実行時のランタイム適用**。`enemies.ts` の敵ステータス・ドロップ・出現プールは
  **不変**(係数を敵定義へ焼き込まない)。
- **AI非波及**(下記)。難易度は決定論の戦闘内部係数であり、DreamMaster・世界変化・会話に影響しない。

### 難易度と係数(被ダメージ倍率)

| id | 表示名 | 被ダメージ倍率(裁量初期値) |
|---|---|---|
| `easy` | やさしい | 0.75 |
| `normal` | ふつう | **1.0(固定・変更禁止)** |
| `hard` | むずかしい | 1.4 |

- 定義は `shared` に追加する: `difficultySchema`(英語 enum `easy`/`normal`/`hard`)・表示名表
  `DIFFICULTY_DISPLAY_NAMES`(やさしい/ふつう/むずかしい)・係数表 `DIFFICULTY_COEFFICIENTS`。
  クライアントは `MAPS`/`ACHIEVEMENTS` と同流儀でこれを直接 import する(表示名を view へ載せない)。
- 倍率は**裁量初期値**で M25-2 の調整可。ただし **`normal` は 1.0 に固定(緩めるも強めるも禁止)**。
- M25-2 は「やさしいは全滅率を下げ、むずかしいは上げる」方向を確認する**新テストを足してよいが、
  既存の `normal` 閾値・判定は一切変えない(緩めない)**(既存統計はすべて `normal`=恒等で不変)。

### 適用点(ダメージ式との関係)

- 現行式(**不変**): `computeDamage = max(1, floor(攻撃力 × 技倍率 × rand(0.9..1.1)) - floor(防御力/2))`。
  variance(`rng.float(0.9,1.1)`)は従来どおり**この関数内で1回だけ消費**する。
- 難易度係数は **`computeDamage` が値を返した後**、**被弾対象がプレイヤーのときのみ**、その
  ダメージ値へ乗算する(単一チョークポイント=`dealDamage` の `target==="player"` 分岐):

  `被ダメ = max(1, floor(computeDamage(...) × 難易度係数))`

  - **RNG消費の後に整数ダメージへ掛けるだけ**なので、乱数列・消費順序・variance のロールは
    一切変わらない(係数は乱数を消費しない)。
  - **ふつう(1.0)は恒等**: `floor(dmg × 1.0) = dmg`、`max(1, dmg) = dmg`(`computeDamage` の
    戻り値は既に `≥ 1`)。よって被ダメ値も HP 推移もターン数も**現状と完全一致**する。
  - やさしい/むずかしい: 減/増後に `floor` し、`max(1, …)` で**最低1ダメージを再保証**(やさしいでも
    プレイヤーは必ず1以上を受ける=既存「最低1ダメージ」規則と整合)。
  - **敵の被ダメージ(与ダメージ)は係数を通さず不変**。
- **係数の運搬**: `createBattle` に第5引数 `difficulty`(既定 `"normal"`)を足す(既存の第4引数
  `equipment` が既定 `createEmptyEquipment()` を取り、テストが省略するのと**同流儀**)。`createBattle` は
  係数を解決し、`BattleState` に `incomingDamageMultiplier`(既定 1.0)として保持する。`dealDamage` は
  この値を読む。`combat-balance.test` は `createBattle` を**3引数で呼ぶ**ため `difficulty=normal`→
  係数 1.0→恒等となり、統計はバイト一致で保存される(`BattleState` はセーブ非対象の一時状態のため
  フィールド追加に `version` 影響なし=M21 状態異常の追加と同じ)。
- **進行中の戦闘は開始時の係数で固定**(戦闘途中で難易度を変えても当該戦闘には遡及せず、次戦から反映)。
